## 1. Контекст и рамки проекта

- **Кто:** владелец стекольного производства, использует Spil Glass ERP (Австралия), недоволен архитектурой типов стекла в текущей БД — считает её изначально неверной.
- **Цель:** не надстройка над Spil, а полная замена. Spil в итоге отключается совсем.
- **Масштаб:** 10–100 заказов в день максимум. Один-два цеха, не сеть заводов.
- **Роль разработчика:** ИИ (Claude) пишет код блоками/модулями постепенно. Пользователь не программист, работает через визуальную итерацию — смотрит готовый экран, а не код или SQL напрямую.
- **Развёртывание:** предпочтение — облако. Локальная копия на ПК допустима на старте, перенос на сервер позже. Часть операций (печать этикеток, выгрузка на станки) физически требует локального агента в цеху — облако до принтера/станка не достаёт.
- **Бюджет времени:** честная оценка полной замены — 15–25 месяцев, по фазам, каждая фаза даёт самостоятельную пользу.

### Ключевой принцип работы с пользователем
Пользователь учится через **визуальную итерацию**, не через код или SQL в чате. Он явно раскритиковал подход "получать сырые .sql файлы" — не может их использовать напрямую. **Каждая часть системы должна поставляться как рабочий HTML/браузерный прототип**, который открывается двойным кликом, без установки, без сервера. Сырой SQL — это внутренний рабочий материал для будущего переноса на сервер, не то, что показывается пользователю.

## 2. Что уже отвергнуто и почему (не предлагать снова)

| Отвергнуто | Причина |
|---|---|
| Миграция/патч текущей БД Spil | Архитектура типов стекла ошибочна с самого начала (закалка была зашита в тип стекла). Решено строить с нуля |
| Импорт клиентов Excel'ем на старте | Отложено — сначала один тестовый клиент + один тестовый тип стекла, клиенты грузятся позже |
| SQL-файлы как основной способ показать прогресс | Пользователь прямо сказал "зачем ты мне даёшь файлы SQL" — нужен рабочий интерфейс |
| Multi-select `<select multiple>` для выбора листов | Непонятно пользователю без Ctrl+клик — заменено на чекбоксы |
| Read-only прототип без возможности редактировать/удалять записи | Пользователь спросил "как потом манипулировать данными" — все сущности получили полный CRUD (добавить/изменить/удалить) с защитой от удаления используемых записей |
| Плоский список типов стекла ("6MM CLR TEMP" как одна строка) | Смешивает подложку, толщину, покрытие и обработку в одну строку — теряет связи, раздувается на сотни строк, не выводит остаток/маршрут/себестоимость |
| Группировка модулей "как удобно вводить" (материалы+покрытия+станки вперемешку) | Пользователь потребовал группировку **по бизнес-домену/владению**: склад/закупки/продажи/производство/отгрузка/финансы — каждый модуль отдельный, со своим отчётом, но связанный через ссылки |
| Хранить весь функционал Glass Configurator в одном большом файле | Частично готовые функции (мунтин ~80%, shape ~40%) мешают друг другу при правках. Решено: каждая специфическая способность — отдельный модуль кода с чётким входом/выходом, подключаемый к сервису (раздел 3, "Декомпозиция на независимые модули") |
| Слово "skill" в значении Claude Skill (SKILL.md/.skill) для этих модулей | Пользователь подтвердил — имел в виду обычный модуль кода, не формат Claude Skills. Не путать |

## 3. Архитектурные решения (стек, платформа)

- **База данных:** PostgreSQL (Supabase или Neon).
- **Бэкенд + фронт:** TypeScript, Next.js. Монолит — не микросервисы, масштаб (10–100 заказов/день) не требует такой сложности.
- **Оптимизатор раскроя: НЕ пишем сами.** Решено интегрироваться с уже используемым **Perfect Cut** (R.O. SRL / Operations Research, perfectcut.glass) вместо разработки своего движка нестинга — это снимает самый тяжёлый и рискованный кусок фазы 3.
  - У пользователя только базовый Perfect Cut, без модулей Perfect Label / Perfect Code / Perfect Stock.
  - Печать стикеров/этикеток уже решена — Perfect Cut печатает их сам на принтере (TCL/TSC). Наш локальный агент печать этикеток НЕ обслуживает.
  - Трекинг детали по станциям цеха и учёт остатков/обрези по-прежнему наши — Perfect Code (штрихкоды) и Perfect Stock (остатки) у пользователя не куплены.
  - **Механизм обмена ещё не подтверждён.** Со слов пользователя: "по нажатии кнопки Perfect Cut получает доступ к батчу" — похоже на прямое подключение к БД Spil (SQL Server) или настроенный коннектор R.O. SRL под Spil, а не на ручной файловый экспорт. План: пользователь посмотрит настройки подключения в Perfect Cut (DSN/строка подключения к Spil) и/или спросит у R.O. SRL, как именно настроен этот коннектор — прямая БД, ODBC или файл, и в каком формате. До получения этой информации формат обмена не проектируется — угадывать его бессмысленно.
  - Локальный агент в цеху меняет назначение: раньше планировался под печать этикеток + выгрузку DXF на станки, теперь его роль — быть мостом данных между нашей БД и Perfect Cut (передать батч на оптимизацию, забрать результат раскроя обратно для трекинга и учёта остатков).
- **Цеховые терминалы:** PWA с офлайн-очередью (IndexedDB), сканирование пишется локально и досылается при восстановлении сети.
- **Локальный агент в цеху:** отдельный маленький сервис на ПК, его подтверждённая текущая роль — **мост данных между облачной ERP и локальным Perfect Cut**. Печать этикеток оставлена Perfect Cut; формат/механизм обмена пока не проектировать до получения реальных настроек коннектора Spil ↔ Perfect Cut. Выгрузка на другие станки может потребовать локальный компонент позже, но конкретный протокол не придумывать заранее.
- **Хостинг:** Vercel/Fly + managed Postgres + ночной дамп на локальный NAS как резервная копия (не второй источник правды).
- **Бухгалтерия НЕ переписывается.** AR/AP, GL, payroll, tax, cash book, fixed assets остаются во внешней системе (QuickBooks/Xero/Sage). Своя ERP только выставляет счёт и передаёт данные наружу. Это решение экономит ~год работы и снимает регуляторный риск.

### Прототипирование — текущий подход
Каждый модуль сначала строится как **самодостаточный HTML-файл** (inline CSS/JS, без зависимостей, открывается локально), с:
- Полным CRUD по всем сущностям (добавить / изменить / удалить с защитой от удаления используемых записей)
- Экспортом/импортом состояния в JSON (кнопки в шапке) — так пользователь сохраняет свою работу между сессиями и присылает её обратно для переноса в реальную БД
- Автосохранением в localStorage браузера
- Валидацией на вводе (обязательные поля, дубликаты, диапазоны)
- Живыми расчётами (проверка маршрута, цена детали) — не просто справочники, а рабочая логика

Когда модель устаканится на прототипе — те же самые экраны переезжают на реальный Next.js + Postgres, меняется только источник данных.

### Декомпозиция на независимые модули (решение от авг 2026)

Пользователь сформулировал принцип: не писать всю функциональность в один файл/модуль, а разбивать каждую специфическую способность (требующую своей геометрии, чертежей, расчётов) на **отдельный модуль кода** — и уже потом подключать его к кнопке или сервису внутри системы.

**Важно про терминологию:** пользователь употребил слово "skill", но явно подтвердил (авг 2026, при уточнении) — имеется в виду **обычный программный модуль**, НЕ формат Claude Skill (SKILL.md/.skill). Не путать эти два понятия при дальнейшей работе. В документе и коде использовать слово "модуль", не "skill", чтобы не создавать путаницу с системой Skills этой платформы.

**Технический контракт модуля:**
- Один файл/папка на одну способность (например `muntin.js`, `free-shape.js`).
- Чёткий вход/выход: модуль получает данные (например размеры камеры, параметры сетки) и возвращает результат (геометрия, DXF-сегменты, BOM) — без обращения к остальной системе напрямую.
- Модуль не знает про цены, клиентов и заказы — эта развязка инженерной логики (геометрия/DXF) от бизнес-логики (цена/клиент) сделана специально: так модуль можно чинить, тестировать и потенциально показать/предложить/продать отдельно, не утаскивая за собой закрытые бизнes-данные.
- Точка подключения — сущность `service` из модели данных (раздел 4.2): у сервиса типа "мунтин" может быть привязан конкретный модуль-калькулятор. Это совпадает с уже существующей моделью услуг в ERP, отдельного нового механизма подключения выдумывать не нужно.

**Решение по конкретным функциям Glass Configurator (авг 2026):** Muntinbar и Shape **переносятся из существующего Configurator, а не переписываются с нуля**. Для текущего ERP-кандидата уже подключена реальная логика **Smart-Shape / Advanced из v4.5** и shape-adaptive **Muntin Production**. При переносе не исправлять известные геометрические баги попутно: сначала сохранить существующее поведение и контракт, затем чинить внутри изолированного модуля отдельными изменениями.

**Критическая связь Shape → Muntin:** Shape является единственным источником размеров и контура детали. Пользователь сначала создаёт/выбирает Shape (Width/Height + Advanced geometry), затем Muntinbar выбирает этот Shape и рассчитывает сетку/длины баров по его реальному контуру. **Не добавлять отдельные Width/Height в Muntinbar** — это создаст второй источник геометрии и риск расхождения.

### Workflow разработки: коммиты напрямую из облака (решение от авг 2026)

Пользователь выбрал: **коммитить код напрямую из этой облачной сессии через GitHub personal access token**, а не через свой подключённый компьютер и не оставаться только на файлах без версионирования.

Согласованная схема:

- Токен передаётся в чат сессии и живёт только в её рамках (session-ephemeral) — не хранится в коде, не коммитится.
- Пушить напрямую в `main` (соло-проект на стадии прототипа, отдельные ветки/PR пока избыточны).
- **Сделано (16 авг 2026):** репозиторий `https://github.com/MaksymPrudnikov/ERP` создан пользователем, код залит — 12 коммитов, 41 файл.
- **Важно про способ заливки:** прямой `git push` из облачной сессии НЕ проходит. У сессии свой git-прокси, он пускает только к репозиториям, добавленным в «sources» задачи, и присланный в чат PAT игнорирует. Первая заливка сделана через веб-интерфейс GitHub браузером пользователя (Claude in Chrome), по одному коммиту на папку. Токен так и не понадобился.

Прямое редактирование файла через веб-редактор GitHub (клик в код → Ctrl+A → печать нового содержимого) на этой сессии оказалось ненадёжным: редактор подвисал на объёме текста с кириллицей и один раз оставил в файле дублированный кусок старого + нового содержимого. **Для замены файла целиком использовать именно загрузку файла (Upload files), не правку в браузерном редакторе.**

### Структура репозитория (решение от авг 2026) — модули отдельными файлами

Пользователь потребовал прямо: **модули отдельно, и подмодули внутри модулей тоже отдельно**, чтобы
чинить по одному и добавлять версии в git, а не пересобирать большой HTML-файл руками.

```
src/core/            dim.js · poly.js
src/modules/shape/   consts · model · contour · validate · geometry · index
src/modules/muntin/  catalog · model · layout · clip · adaptive · bom · drawing · index
src/erp/             data · icons · i18n · nav · storage + views/*
```

- Разбиение сделано **чистым переносом текста**: собранный файл байт-в-байт совпал с исходным кандидатом по коду (проверено сравнением и одинаковыми числами геометрии в трёх сборках).
- Правило: **правку вносить в один маленький модуль, потом `node build/build.js`.** Полный HTML заново не собирать.

## 4. Ядро модели данных — материалы и стекло

### 4.1 Главный принцип: разделение осей
**Материал = подложка + толщина + покрытие.** Обработка (закалка) НЕ входит в материал — на складе закалённого стекла не бывает, закалку делает сам цех. Название и вес не хранятся полями — вычисляются из связанных таблиц.

Было неправильно: `6MM CLR TEMP` как одна строка справочника.
Стало правильно: `substrate(CLR) + thickness(6mm) + coating(null) → material`, а `treatment(TEMP)` — отдельная сущность, применяется к детали в процессе, не к материалу на складе.

### 4.2 Таблицы (реализованы в SQL-миграциях 01–05)

**`substrate` (подложка)** — тело стекла как сварил завод. БЕЗ толщины, покрытия, обработки.
- `code`, `name`, `family` (clear/low_iron/tinted/patterned/wired/other)
- `tint_colour_code` (FK, обязателен только для tinted)
- `density_kg_m3` (нужен для веса детали: вес = плотность × толщина × площадь)
- `is_temperable`, `is_laminatable`, `is_directional` (узорчатое стекло имеет лицевую сторону)
- `legacy_code` (маппинг на старые артикулы Spil)
- CHECK: tinted обязан иметь tint_colour; wired не может быть temperable (физическое ограничение)

**`coating` (покрытие)** — покрытие как продукт. Номер поверхности (#2, #3, #4) — свойство СЛОЯ ИЗДЕЛИЯ, не покрытия.
- `coating_type` (low_e/solar_control/reflective/mirror/self_cleaning/anti_reflective/etch)
- `deposition` (pyrolytic твёрдое / sputtered мягкое / chemical / applied)
- `applied_by` (primary_manufacturer / offline_coater / **fabricator** — если наносим сами, это генерирует шаг маршрута, а не позицию закупки)
- `temper_mode` — **тройное состояние, не булево**: `annealed_only` / `temperable` / `temper_required` (свойства раскрываются только после закалки)
- `exposure_rule` (any/cavity_only/exterior_only/interior_only) — рабочий пример: **i89 от Cardinal работает на поверхности #4, внутрь помещения**, а не в камеру, в отличие от всех остальных low-E. Это ловится constraint'ом `coating_mirror_rules` и полем exposure_rule.
- `requires_edge_deletion` + `edge_deletion_width_mm` (согласованы constraint'ом)
- `emissivity`, `shelf_life_days` (мягкие покрытия окисляются, партия имеет срок годности)
- Правило разделения покрытие vs услуга: *если две партии взаимозаменяемы и могут лежать на одной стойке — это покрытие; если задаётся под конкретный заказ (рисунок, %, цвет) — это услуга.* Шелкография = услуга (`line_service`), зеркало/сатин = покрытие (`applied_by = offline_coater`).

**`thickness` (толщина)** — номинал ≠ факт. "6мм" это обозначение, не измерение.
- `nominal_mm`, `imperial_label`, `actual_mm`, `is_verified`
- **Важно:** фактическая толщина в итоге переехала на уровень `material`, а не осталась только в `thickness` — потому что разные линии дают разный факт при одном номинале (6mm Clear = 5.77мм, 6mm LoE-272 = 5.70мм). `material.actual_thickness_mm` перекрывает значение из `thickness.actual_mm`.

**`material`** — единица закупки/склада. `substrate_id + thickness_id + coating_id(nullable) → уникальная связка`. Плюс `actual_thickness_mm`, `thickness_verified`, `legacy_code`.

**`supplier` / `source` (точка поставки)** — отделены друг от друга. Один поставщик может иметь несколько точек поставки с РАЗНОЙ ВАЛЮТОЙ: Vitro Barrie в CAD, Vitro USA в USD, Cardinal USA в USD. Валюта принадлежит точке поставки, не поставщику.

**`sheet_size` (типоразмер листа)** — зависит от ПАРЫ материал+поставщик, не глобален. Vitro продаёт 144×100", Cardinal тот же условный "144" даёт как 144×96". Таблица связи `material_supply_sheet`.

**`treatment` (обработка)** — закалка/HS/отжиг как процесс.
- `is_heat_treated`, `requires_furnace`
- **`can_cut_after`** — главное поле: false у закалки/HS/HST. Отсюда следует весь порядок маршрута: рез, кромка, отверстия — всё ДО печи, размер реза = финальный размер.
- `strength_factor` (HS ≈2x, tempered ≈4x относительно annealed)

**`work_center` (станок/рабочий центр)** — физическое ограничение оборудования.
- `max_width_in`, `max_length_in`, `min_width_in`, `min_thickness_mm`, `max_thickness_mm`
- Заведено: печь закалки `FURN1` (90×150"), кромкообработка `EDGE1`, фацетный станок `BEVEL1` (70×100"), ЧПУ `CNC1` (60×122")
- **Ключевой инсайт:** максимальный размер детали — НЕ константа, а функция от МАРШРУТА через набор станков. Одна и та же деталь может проходить через печь, но не проходить фацетный станок (разные лимиты). Функция `check_route_fits()` / `checkRoute()` в JS-прототипе проверяет весь список операций разом и возвращает все нарушения.
- Печь 90×150" не берёт лист 130×96" целиком (96 > 90 по короткой стороне) — целый лист закалить нельзя, только раскроенные детали.

**`service` (услуга)** — притупление кромки, полировка, фацет, сверловка, ЧПУ.
- `stage`: pre_temper (вся механика — закалённое стекло не обрабатывается) / post_temper / any
- `affects_size` — операция съедает материал, размер реза больше финального
- `service_allowance` — припуск на рез, зависит от услуги И толщины, отдельно ширина/высота (SEAM 0, POLISH 1/16", BEVEL 1/8", CNC 1/4" — для 6мм)
- `service_work_center` — связь услуга↔станок, лимиты можно переопределить на уровне связки

### 4.3 Данные пользователя (реальные, уже введены)

## 5. Ценообразование (только что спроектировано, нужно доработать)

### 5.1 Бизнес-правила от пользователя
- Модель: **закупка по себестоимости → своя наценка → плюс услуги → плюс energy surcharge**.
- Минимальная площадь к оплате: **4 ft²** по умолчанию, но может быть **2 или 3 ft²** для отдельных случаев (переопределение на уровне материала или клиента).
- Округление размера для расчёта площади к оплате: **вверх до целого дюйма** (23.25" → 24"). Это отдельно от размера реза/себестоимости, который считается по факту с припусками.
- Валюта закупки зависит от точки поставки (см. `source` выше), не от материала напрямую.
- **Профит НЕ виден никому кроме админа и специально допущенных пользователей.** Это касается всей цепочки: цена закупки, точка поставки, фрахт, курс, себестоимость, маржа/наценка в процентах, отчёты P&L. Наценка в процентах тоже скрывается — иначе через неё вычисляется себестоимость. Скрытие должно быть на уровне ВЫДАЧИ ДАННЫХ (API/отчёт/экспорт), не только на уровне экрана — иначе Excel-экспорт или печатная форма всё равно унесёт цифры.

### 5.2 Что уже реализовано в прототипе v3
- Разделение: **фактическая площадь** (для себестоимости, с припусками на услуги + % отхода) vs **площадь к оплате** (округлённая, с учётом минимума).
- `costOf(material)` — тянет последнюю по дате цену закупки, конвертирует по курсу FX в базовую валюту, добавляет % фрахта.
- `priceLine()` — полная раскладка: размер после округления → площадь факт → площадь к оплате → размер реза с припусками → расход с отходом → себестоимость → цена продажи (наценка) → построчно услуги/обработка по их ценам → подытог → energy surcharge → итог за деталь → итог × количество.
- Таблицы: `fx` (курсы), `cost` (цены закупки по материалу+точке поставки+дате), `servicePrice`, `treatPrice`, `settings` (базовая валюта, округление, минимум ft², % отхода, % наценки, % energy surcharge).

### 5.3 Ещё не сделано / открытые вопросы по цене
- Права видимости профита (роль/пользователь → что скрыто) — спроектировано словами, не реализовано в коде.
- Цены/скидки по конкретным клиентам, скидки от объёма, надбавка за срочность — отложено до модуля заказа/клиента.
- Реальные цены закупки — сейчас в прототипе везде 0, пользователь должен заполнить сам.
- Курс USD→CAD сейчас захардкожен как 1.37 — нужно подтвердить/обновить.

## 6. Модульная структура (актуальное решение — переработать группировку)

Пользователь потребовал: **модули по бизнес-домену/владению**, не по "удобству ввода". Каждый модуль отдельный, но связан через ссылки, и у каждого должен быть СВОЙ ОТЧЁТ (что/как/сколько делалось).

| Модуль | Владеет данными | Отчёт |
|---|---|---|
| **Склад / инвентаризация** | Номенклатура, материалы, подложки, покрытия, толщины, листы; остатки, партии, обрезь, движения | Расход, оборачиваемость, что лежит мёртвым грузом |
| **Закупки** | Поставщики, точки поставки, цены закупки, заказы поставщику, приёмка, MRP | Динамика цен, поставки в срок, недопоставки |
| **Продажи** | Клиенты, прайсы, скидки, котировки, заказы, ACK | Выручка, маржа по продукту (скрыто не всем), конверсия котировок |
| **Производство** | Станки, услуги, маршруты, план, детали в работе, бой и перезаказ | Выработка, загрузка станков, брак и причины |
| **Отгрузка** | Стойки, комплектация, маршруты, накладные | Отгружено в срок, простой стоек |
| **Финансы** | Фактическая себестоимость, счета, интеграция с бухгалтерией | P&L по продукту, где теряется маржа |

**Ядро (общее для всех модулей, не отдельный модуль):**
- Единицы измерения, валюты, курсы
- Пользователи и права
- **Журнал событий** — критично: отчёты "что как сколько делалось" читаются ИЗ ИСТОРИИ СОБЫТИЙ, не из текущего состояния таблиц. Текущее состояние БД не хранит "сколько закалили в июле" — если события не писать с первого дня, задним числом это не восстановить. Каждое действие в любом модуле обязано писать событие: кто, что, когда, сколько, над каким объектом.

**Важно:** прототип v3 (файл glass_erp_v3.html) сгруппирован ПО-СТАРОМУ — вкладки "Материалы / Каталоги / Производство / Закупка / Продажа / Расчёт". Это НЕ переделано и остаётся как справочный прототип модели материалов/цены, не как основа для дальнейшей доменной структуры.

**Доменная оболочка построена и живёт в репозитории** — состав экранов и что в них реально работает см. раздел 10. Кратко: Dashboard, Users, Sales / configuration (Smart-Shape + Adaptive Muntin), Optimization, Production. Домены Inventory / Purchasing / Shipping / Finance пока только в меню.

**Чего в оболочке ещё нет из требований этого раздела:**
- журнала событий — а без него отчёты «что как сколько делалось» построить нельзя задним числом;
- собственных отчётов у каждого домена;
- модель материалов и цены (разделы 4–5) в новую оболочку не перенесена, остаётся в справочном `glass_erp_v3.html`.

## 7. Права доступа (спроектировано словами, не реализовано)

- **Сейчас:** только админ (стадия разработки).
- **В перспективе:** разделение по модулям, для каждого — просмотр vs изменение.
- **Уровней не два, а четыре:** нет доступа / просмотр / изменение / **согласование** (например кладовщик может списать бой, но не может утвердить списание — разные права на одно действие).
- **Права нужны и на уровне полей, не только модулей.** Пример: продажник видит цену продажи, но не видит себестоимость и маржу — это одна колонка внутри ЕГО ЖЕ экрана заказа, не "доступ к модулю Финансы" целиком.
- **Профит закрыт по умолчанию** — только админ + явно допущенные пользователи (см. раздел 5.3).
- **Архитектурное решение:** одна точка проверки прав — функция вида `можно(роль/пользователь, модуль, действие)`, вызываемая при КАЖДОМ действии. Не размазывать проверки по интерфейсу — иначе разделение прав станет отдельным проектом на месяц вместо правки одной таблицы.
- **Проверка должна быть на уровне выдачи данных (API), не на уровне UI** — спрятанная кнопка/колонка не защита, данные всё равно приедут в браузер через тот же запрос.
- **Цеховые терминалы — особый случай:** учётка принадлежит станции/терминалу, а не человеку; конкретный оператор идентифицируется сканом бейджа при действии. Если заставлять логиниться/разлогиниваться на каждой смене — операторы будут работать под одной общей учёткой, и журнал событий (см. раздел 6) станет бесполезным.
- Роли пользователя ещё не названы явно (ожидается: продажи, технолог/инженер, цех, отгрузка, снабжение, руководство, админ) — нужно уточнить у пользователя.

**Не проверено отдельно:** визуально на реальных нестандартных Shape (трапеция/скошенные углы) через сам интерфейс — проверка была только через regression-тесты (`test/run.js`, эталонные числа) и байтовое сравнение файлов. Если пользователь увидит визуальные огрехи на конкретной фигуре — заводить как новую правку, не считать этот аудит финальным.

## 11. Открытые вопросы / что нужно от пользователя дальше

**Нужны данные от производства:**

1. **Печь:** минимальный размер детали и максимальный вес садки (есть только рабочее поле 90 × 150″).
2. **Уровень потока для CNC1 и FURN1** — неясно, ЧПУ это кромка/полировка (уровень 2) или сверловка/паз (уровень 3), и куда встраивается закалка. Решает только пользователь, не угадывать.
3. **Полный список станков** — заведены четыре (печь, кромка, фацет, ЧПУ). Нужны мойка, линия IGU, автоклав, ламинация и остальные, с габаритами.
4. **В каких толщинах реально доступно каждое покрытие** — засеяно только под 6 мм.
5. **Реальные цены закупки** по каждому материалу — в прототипе везде 0.
6. **Курс USD→CAD** — захардкожен 1.37, подтвердить или обновить.
7. **Роли пользователей** в компании (продажи / технолог / цех / отгрузка / снабжение / руководство) — нужны для проектирования прав доступа.
8. **Механизм обмена Perfect Cut ↔ Spil** — настройки подключения из Perfect Cut и/или ответ R.O. SRL. До этого формат моста не проектировать.

**Технические решения, ожидающие ответа:**

9. **Перевод сообщений модулей.** `Shape not found`, `Shape is invalid` приходят из модулей по-английски и в русском интерфейсе не переводятся. Модуль не должен знать про язык оболочки — правильное решение это коды ошибок плюс перевод в оболочке. Решить, делать ли сейчас.
10. **Журнала событий нет.** Раздел 6 требует писать событие на каждое действие в каждом модуле. В прототипе не реализовано — это отдельный слой ядра, не правка экрана. Чем позже начать, тем больше истории потеряно безвозвратно.
11. **Донести SQL-миграции и xlsx-шаблон** в репозиторий (см. раздел 10).
12. **Визуальное направление.** Пользователь одобрил общий рост визуальности, но оценил как «лучше, но не идеально ни визуально, ни логически». Следующая итерация — по его конкретным замечаниям, без самостоятельного большого редизайна.
13. **Адаптация под мобильный экран.** Визуализация (чертёж Muntin) на телефоне ломается — подтверждено пользователем 17 авг 2026, но осознанно отложено: сначала стабилизировать саму логику построения чертежа (сейчас на модулях Shape/Muntin ещё идут правки), потом отдельным проходом адаптировать интерфейс/CSS под маленький экран. Сам SVG чертежа уже строится через `viewBox` независимо от размера экрана — это не требует доработки; ломается именно окружающий UI (панели/кнопки/таблицы), которым и предстоит заняться в этом отдельном проходе.

## 12. Инструкция для продолжения (для ИИ, который подхватит проект)

**Про код и репозиторий**

- Код живёт в `MaksymPrudnikov/ERP`, разрезан на 28 модулей. **Не присылать пользователю новый большой HTML «взамен»** — правится ОДИН модуль в `src/**`, дальше робот сам пересоберёт `dist`. Пересборка файла целиком руками — ровно то, от чего пользователь отказался.
- **Перед правкой геометрии прогнать `node test/run.js`, после правки прогнать снова.** Эталонные числа там не для красоты: трапеция 48 × 36 при C = 30 обязана давать бары `33 7/64″ · 31 1/8″ · 47 1/8″`. Разошлось — сломан перенос v4.5, а не тест.
- **Добавил файл в модуль — впиши его в `build/manifest.json` и `src/index.html`**, в одинаковом порядке. Иначе `check-manifest` остановит сборку.
- **Исправления известных особенностей v4.5 — отдельным коммитом**, не смешивая с изменением интерфейса, чтобы можно было откатить одно, не потеряв другое.
- **Прямой `git push` из облачной сессии Claude (Cowork) не проходит** — прокси пускает только к репозиториям, добавленным в «sources» задачи. Либо добавить репозиторий в источники при старте задачи, либо заливать через `Upload files` на GitHub (не через встроенный редактор — см. раздел 3). `device_bash` на машине пользователя работает без сети, git оттуда невозможен. В Claude Code (CLI) этого ограничения нет — push идёт напрямую.

**Про архитектуру — не переизобретать**

- Не предлагать миграцию базы Spil: решение строить с нуля финальное.
- Не проектировать свой оптимизатор раскроя — интеграция с Perfect Cut (раздел 3).
- Не изобретать формат обмена с Perfect Cut, пока не пришли реальные настройки коннектора.
- Уважать разделение осей из раздела 4: подложка / покрытие / толщина / обработка, тройное состояние `temper_mode`, `exposure_rule`.
- Новый модуль — сверяться с картой доменов (раздел 6), не мешать сущности разных доменов в один экран.
- Права доступа — через единую точку проверки (раздел 7), не размазывать по экранам, проверять на выдаче данных, а не в интерфейсе.
- Каждое действие в любом будущем модуле обязано писать событие в журнал (раздел 6).

**Про модули Shape и Muntin**

- Перенесены из Glass Configurator v4.5, **не переписываются с нуля**. Не «улучшать» геометрию попутно без отдельного тестового шага.
- **Не добавлять размеры стекла в Muntinbar.** Width/Height и контур принадлежат Shape; Muntinbar получает выбранный Shape по ссылке. Один источник геометрии — намеренно. Проверяется тестом.
- Модуль не знает про цены, клиентов и заказы. Эта развязка сделана специально.
- Слово «модуль» = обычный файл с кодом, **не** формат Claude Skills. Не путать.
- **Чертёж (`drawing.js`) обновлён 17 авг 2026** — прямоугольные и Shape-детали используют разные, но согласованные схемы простановки размеров, см. раздел 9а перед тем как трогать этот файл снова.

**Про интерфейс**

- Shape и Muntinbar показывать отдельными иконками-карточками, не текстовым списком. Навыки сотрудников — тоже иконками, где это помогает читать.
- **RU/EN переводит интерфейс, а не данные.** Значения из базы выводить через `raw()`; `esc()` для пользовательских значений больше не использовать, иначе переводчик снова начнёт менять содержимое базы.
- **Мобильная адаптация сознательно отложена** (см. раздел 11, пункт 13) — не начинать без явного запроса пользователя, чтобы не переделывать по два раза при продолжающихся правках Shape/Muntin.

**Про общение**

- Стиль — русский/украинский смешанный, конкретно, без лишней теории, всегда с примерами на реальных данных пользователя (Vitro, Cardinal, конкретные толщины и станки).
- Пользователь не программист и учится через визуальную итерацию. Сырой SQL как единственный артефакт не годится — всегда рабочий экран.
- При обновлении этого документа — **точечные правки в нужный раздел, не переписывать файл целиком.** Так прямо просил пользователь.
