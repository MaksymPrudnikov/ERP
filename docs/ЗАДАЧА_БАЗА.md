## Зачем

Сейчас вся база ERP — один объект `DB` в памяти. Каждое действие
записывает её целиком одной строкой в `localStorage` (`src/erp/storage.js`,
`touch()`).

- **Лимит.** Браузер даёт около 5 МБ: неделя цеха — 4,3 МБ, 14 месяцев из
  `tools/sim-shop.js` — 100 МБ.
- **Скорость растёт вместе с историей.**
  - Каждое действие дважды делает `JSON.stringify` всей базы
    (`storageCommand` + `touch`).
  - Save заказа заново нормализует все заказы (`normalizeSalesData`).
  - Другие вкладки после каждой записи заново разбирают всю базу
    (`storageLiveReload` → `prepareImportedState`).
  - Отчёты перебирают всю историю.
  - Доказательство: симулятор сам прячет старые заказы в свой архив
    (`tools/sim-shop.js:1348–1420`) — «на 14 месяцах это секунды на каждый
    Save».
- **5–7 лет (0,5–0,7 ГБ) в нынешней модели не работают вообще.** Строка
  такого размера не создаётся (предел V8 ≈ 0,5 ГБ), памяти нужно несколько
  ГБ.

## Решения владельца (20.10.2026)

- **Без двойной работы.** В будущем возможен сервер с данными за 7 лет,
  в том числе с проектами прошлых лет. Поэтому
  хранение сразу строится так, как будет на сервере: по записям, с архивом
  и ленивой загрузкой. Временного решения «вся база одной строкой в
  IndexedDB», которое потом выбросить, не делаем.
- **Старт пустой.** Живых данных нет, всё тестовое. Переноса из
  `localStorage` нет; старый ключ `glazing_system_v1` не читаем и не
  удаляем.
- **Испытания сейчас** — год цеха в полном объёме со складом плюс запас:
  24 месяца (двойной объём и два перехода года). После архива — ещё 7 лет.
- **Пороги «быстро»:**
  - скан на станции ≤ 0,3 с;
  - Save и любой клик ≤ 0,5 с;
  - открыть экран ≤ 1 с;
  - F5 ≤ 5 с.
  - Выше — красным.
- **Архив должен уметь все четыре вещи:**
  - найти и открыть старый заказ: по номеру, клиенту, PO; документы,
    печать;
  - повторить заказ — копия в новый;
  - рекламация (NCR) и переделка по старому заказу;
  - отчёты за прошлые годы и сравнение год к году.
  - Через сколько месяцев после закрытия заказ уходит в архив — спросить
    на этапе 3. Это одна константа, не настройка.
- **Бесплатно сейчас.**

  - Этап 4 — Supabase Free, проект `glass-erp-test`.

## Главный принцип: одна модель записей — три места хранения

- **Запись** — `{tbl, id, seq, data}`. Один заказ, один скан, одно стекло.
  - `tbl` — ключ таблицы в `DB` (`salesOrder`, `stationScan`…).
  - `id` — `id`, иначе `code`, иначе ключ, выбранный для таблицы. Таблица
    без ключа — одна запись `'*'`. Не массивы — записи таблицы `_meta`.
  - `seq` — порядок в массиве: порядок в `DB` важен — «новые» по
    `slice(-60)`, сортировки по номеру.
- **Три места хранения одной и той же записи:**
  1. **Память** — `DB`, только горячие записи. Разделы работают с `DB`, как
     сейчас: их код не переписывается.
  2. **IndexedDB** — все записи устройства: горячие и архив. Сейчас это
     единственная база; при сервере — его кэш.
  3. **Сервер** (этап 4) — `erp_record (tbl, id, seq, data, rev, …)` в
     Postgres; та же запись.
- **Действие** = набор изменённых записей (change-set). Его пишет IndexedDB
  одной транзакцией, его получает другая вкладка, его же потом отправим на
  сервер. Целиком база больше не пишется.
- **Архив** — те же записи, просто не загруженные в память. Открытие —
  асинхронный запрос: к IndexedDB сейчас, к серверу потом. Код разделов не
  знает, откуда пришло.
- **Слой хранения — один интерфейс, два исполнителя**: локальный
  (IndexedDB, этапы 1–3) и серверный (этап 4).
  - Операции: загрузить горячее; записать change-set; получить записи по
    ключам; найти в указателе архива; принять чужие изменения с `rev`.

   сервер узнаёт номер и не записывает второй раз: оплата не задвоится,
   скан тоже.
2. **Конфликт — только по тому, что действие трогает.** Скан на станции и
   оплата в офисе друг другу не мешают. Два ПК правят один заказ — кто
   первым дошёл до сервера, тот записан; второй видит «Changed on another
   device — not saved», набранное остаётся у него на экране (как карточка
   клиента с v5.204). Две отгрузки одного стекла — конфликт, даже если
   накладные разные. Владельцу объяснено примерами 22.10 (один заказ у двоих,
   две накладные на одни юниты, обрыв сети); возражений нет.
3. **Без интернета работа идёт.** Команды ждут в очереди на диске
   устройства, переживают F5 и выключение, уходят по порядку, когда сеть
   вернётся. Внизу видно: «сохранено здесь · ждёт сервера N · отклонено».
4. **Номера — подряд, без дыр** (владелец, 22.10: «дыры нам не надо, нужно,
   чтобы всё было логически структурировано и правильно»). Номера заказов,
   квот, счетов, PS, PO, NCR, стёкол G- и юнитов U- выдаёт только сервер,
   по порядку, в момент записи. Пачек нет. Без интернета заказ сохраняется,
   номер ждёт сети («номер ждёт сети»); стикеры стекла без G- — после
   связи. Пропуск — только при Delete, как и сейчас.
5. **Вход — по человеку, не по устройству** (владелец, 22.10: «устройства
   иногда кочуют… люди входят под своим логином и паролем, вообще не
   привязывайся к устройству»). Офис — имя и пароль, станция — личный номер
   и PIN; это персональные входы на сервер; входов устройств нет. Сервер
   знает, кто что сделал, и сам проверяет галочки разделов.
6. **Права проверяет сервер, а не только экран.** Без галочки Finance
   человек не получает оплат, Users — только администратору. **Цены не
   доходят до тех, кому их не показывают** (владелец, 22.10: «цены не должны
   доходить до пользователя»): без раздела с деньгами (Sales, Finance;
   Shipping — только баланс заказа) сервер отдаёт заказ без цен и сумм.
   Правку такого человека в заказе (станция ставит «резка началась») сервер
   сливает с ценами из базы — цены не стираются.
7. **Старая версия ERP не пишет на сервер.** Сервер отклоняет команды
   устаревшей сборки — как сейчас вкладка старой версии не пишет в базу.
8. **ПК, выключенный месяц, догоняет правильно.** Удаления и уход в архив
   доходят и до него; отстал сильнее, чем хранит сервер, — перечитывает
   работу целиком, ничего своего неотправленного не теряя.
9. **Свой адрес сайта и HTTPS** для настоящих данных (не
   `maksymprudnikov.github.io`, который делят пять сайтов) — к «Чистому
   старту».

**Для исполнителя**
- Таблицы: `erp_record (tbl, id, seq, data jsonb, cold, month, ver,
  deleted, updated_at, updated_by)`, PK `(tbl, id)`; `erp_log (rev
  bigserial, tbl, id, ver)` — курсор изменений; `erp_command (id PK,
  device, build, at, result jsonb)` — повтор команды возвращает прежний
  ответ; `erp_counter (name, next)`.
- Запись — RPC `erp_apply(command_id, build, expect[{tbl,id,ver}],
  changes)`: всё или ничего; конфликт — если `ver` хоть одной ожидаемой
  записи не совпал (не общая `rev` всей базы); бизнес-условия (одно стекло
  — одна активная отгрузка) — проверкой в той же транзакции. Ответ — новые
  `ver` и `rev`.
- Чтение — `erp_changes(since_rev, limit)` с удалениями (tombstone);
  `since_rev` старше хранимого журнала — сигнал «перечитать горячее».
  Холодное (архив) — по запросу, `cold` и `month` в той же таблице.
- Номера — `erp_next(name)` внутри `erp_apply`, подряд, в той же транзакции,
  что и запись; команда без сети несёт временную метку, номер ставит
  сервер; клиент заменяет метку номером по ответу.
- Вход — Supabase Auth, пользователь на человека (офис — имя и пароль;
  станция — номер и PIN через RPC входа); галочки человека → какие `tbl`
  читать и писать (RLS по таблице, не «только вошедшим»); `updated_by` —
  человек. Очередь без сети уходит от имени того, кто сделал действие.
- Деньги в заказе: список полей цены и сумм (`priceManual`, `priceOverride`
  панелей и полостей, `priceBook`, `adjustments`, сборы, `chargePricing` и
  подобные — составить по коду до этапа 4); чтение без права денег — RPC
  отдаёт `data` без них; запись без права денег — сервер возвращает эти поля
  из хранимой версии. Тест: станция правит заказ — цены в базе те же. RPC —
  `SECURITY DEFINER`, `search_path` закреплён, `EXECUTE` только
  authenticated; прямая запись в таблицы запрещена. `service_role` — только
  инструменты на Mac владельца.
- Клиент: очередь команд в IndexedDB (`queued → sent → done | rejected`),
  локальное применение до ответа, откат отклонённого с понятной причиной;
  опрос `erp_changes` раз в 3 с, реже в скрытой вкладке.
- Архив (этап 3) строится уже под это: у записи `cold` и `month`; сравнение
  базы не считает незагруженное холодное удалённым; Export/Import/копия —
  с холодным; уход в архив и возврат — обычная команда (change-set).
- Проверка — на настоящем Postgres (локальный `supabase start`), не только
  `page.route`: потерянный ответ после записи, повтор `command_id`, две
  команды наперегонки на одно стекло, устаревшая сборка, обрыв сети
  посреди смены сканов, восстановление копии; отрицательные: Sales читает
  Finance, станция пишет Users, прямой вызов RPC без входа.
