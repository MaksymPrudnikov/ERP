## Зачем

Сейчас вся база ERP — один объект `DB` в памяти. Каждое действие
записывает её целиком одной строкой в `localStorage` (`src/erp/storage.js`,
`touch()`).

- **Лимит.** Браузер даёт около 5 МБ: неделя цеха — 4,3 МБ, 14 месяцев из
  `tools/sim-shop.js` — 100 МБ.
- **Скорость растёт вместе с историей.**
  - Каждое действие дважды делает `JSON.stringify` всей базы
    (`storageCommand` + `touch`).
  - Save заказа заново нормализует все заказы (`normalizeSalesData`).
  - Другие вкладки после каждой записи заново разбирают всю базу
    (`storageLiveReload` → `prepareImportedState`).
  - Отчёты перебирают всю историю.
  - Доказательство: симулятор сам прячет старые заказы в свой архив
    (`tools/sim-shop.js:1348–1420`) — «на 14 месяцах это секунды на каждый
    Save».
- **5–7 лет (0,5–0,7 ГБ) в нынешней модели не работают вообще.** Строка
  такого размера не создаётся (предел V8 ≈ 0,5 ГБ), памяти нужно несколько
  ГБ.

## Решения владельца (20.10.2026)

- **Без двойной работы.** В будущем возможен сервер с данными за 7 лет,
  в том числе с проектами прошлых лет. Поэтому
  хранение сразу строится так, как будет на сервере: по записям, с архивом
  и ленивой загрузкой. Временного решения «вся база одной строкой в
  IndexedDB», которое потом выбросить, не делаем.
- **Старт пустой.** Живых данных нет, всё тестовое. Переноса из
  `localStorage` нет; старый ключ `glazing_system_v1` не читаем и не
  удаляем.
- **Испытания сейчас** — год цеха в полном объёме со складом плюс запас:
  24 месяца (двойной объём и два перехода года). После архива — ещё 7 лет.
- **Пороги «быстро»:**
  - скан на станции ≤ 0,3 с;
  - Save и любой клик ≤ 0,5 с;
  - открыть экран ≤ 1 с;
  - F5 ≤ 5 с.
  - Выше — красным.
- **Архив должен уметь все четыре вещи:**
  - найти и открыть старый заказ: по номеру, клиенту, PO; документы,
    печать;
  - повторить заказ — копия в новый;
  - рекламация (NCR) и переделка по старому заказу;
  - отчёты за прошлые годы и сравнение год к году.
  - Через сколько месяцев после закрытия заказ уходит в архив — спросить
    на этапе 3. Это одна константа, не настройка.
- **Бесплатно сейчас.**
  - Этапы 1–3 — IndexedDB в браузере: гигабайты, без сервера.
  - Этап 4 — Supabase Free, проект `glass-erp-test`.

- **Устройства.** У владельца MacBook, у остальных — слабые Windows-ПК.

## Главный принцип: одна модель записей — три места хранения

- **Запись** — `{tbl, id, seq, data}`. Один заказ, один скан, одно стекло.
  - `tbl` — ключ таблицы в `DB` (`salesOrder`, `stationScan`…).
  - `id` — `id`, иначе `code`, иначе ключ, выбранный для таблицы. Таблица
    без ключа — одна запись `'*'`. Не массивы — записи таблицы `_meta`.
  - `seq` — порядок в массиве: порядок в `DB` важен — «новые» по
    `slice(-60)`, сортировки по номеру.
- **Три места хранения одной и той же записи:**
  1. **Память** — `DB`, только горячие записи. Разделы работают с `DB`, как
     сейчас: их код не переписывается.
  2. **IndexedDB** — все записи устройства: горячие и архив. Сейчас это
     единственная база; при сервере — его кэш.
  3. **Сервер** (этап 4) — `erp_record (tbl, id, seq, data, rev, …)` в
     Postgres; та же запись.
- **Действие** = набор изменённых записей (change-set). Его пишет IndexedDB
  одной транзакцией, его получает другая вкладка, его же потом отправим на
  сервер. Целиком база больше не пишется.
- **Архив** — те же записи, просто не загруженные в память. Открытие —
  асинхронный запрос: к IndexedDB сейчас, к серверу потом. Код разделов не
  знает, откуда пришло.
- **Слой хранения — один интерфейс, два исполнителя**: локальный
  (IndexedDB, этапы 1–3) и серверный (этап 4).
  - Операции: загрузить горячее; записать change-set; получить записи по
    ключам; найти в указателе архива; принять чужие изменения с `rev`.

  - Повторить — копия в новый заказ.

  - Отчёты: итоги каждого месяца пишутся при отправке в архив (продажи,

## Этап 4 — сервер: Supabase (подробный план — владельцу до кода)

- **Спросить владельца до кода:**
  1. Номера стёкол, юнитов, сканов, обрезков, PS, PO, NCR, заказов выдаёт
     устройство: `glassPieceSeq`, `glassUnitIdSeq`, `stationScanSeq`,

     блоки номеров с сервера. Допустимы ли пропуски и непорядок? Для
     каких номеров нет? (`id` записей уже уникальны: `salesUid` —
     `crypto.randomUUID()`.)
  2. Один вход на все устройства или свой на каждое.
  - (Решено 20.10: настоящие данные появляются только с переездом на
    сервер — «Чистый старт».)
- **Владелец делает сам** (пошаговая инструкция с картинками):
  - supabase.com → проект `glass-erp-test`, регион ближе к цеху;
  - выключить регистрацию;
  - завести входы;
  - SQL Editor → `tools/supabase/schema.sql`;
  - адрес и publishable (anon) ключ.
  - service_role — в браузер никогда.
- **Схема** — та же запись:
  - `erp_record (tbl, id, seq, data jsonb, cold, rev, deleted,
    updated_at, updated_by)`, PK `(tbl,id)`, индекс по `rev`;
  - RLS — только вошедшим;
  - запись — RPC `erp_put(changes)`: change-set целиком, с проверкой
    ожидаемой `rev`, всё или ничего, `pg_advisory_xact_lock`, чтобы `rev`
    шли по порядку;

    `glazing_system_v1-id-mark` (`glassIdMarkApply`) не перепрыгивает
    блок;
  - RPC размера базы — в индикатор места (80 % от 500 МБ).
- **Серверный исполнитель слоя хранения** (интерфейс этапа 1):
  - загрузить горячее (первый раз — с сервера, дальше из IndexedDB-кэша);
  - change-set → `erp_put`, очередь в IndexedDB без сети;
  - чужие изменения — опрос раз в 3 с `rev > N` (реже, когда вкладка
    скрыта);
  - архив — по запросу с сервера (этап 3 уже асинхронный).
  - Устройство не скачивает 7 лет: только горячее и открытое.
- **Конфликт** — отклонить действие, подтянуть свежее, «Changed on another
  device — not saved». Формы уже сверяют версии (`cSeen`, `mdSeen`,

- **Нет сети или проект уснул** — «Offline · N waiting»; владельцу — где
  Restore.
  - Интернет в цеху с перебоями, поэтому очередь — главная часть.
  - Сканы и Save работают без сети, после возврата сети уходят по порядку.
  - Тест обрывает сеть посреди смены сканов и проверяет, что ничего не

- **Вход** — `fetch` к `/auth/v1/token`. Форма Cloud в Users

- **Первая заливка** — Export v2 → сервер пачками. Замерить.
- **Ограничение испытаний:** отпечатки паролей (`DB.user`) видны вошедшим
  устройствам. Для живого цеха — правила из хендоффа v5.109.
- **Тест без интернета:** `test/cloud-sync.js` — два «устройства» (два

  - номера не совпадают;
  - конфликт;

## Чистый старт = переезд на сервер (когда владелец скажет)

Владелец, 20.10.2026: чистый старт будет вместе с переездом на облачный
или физический сервер. Настоящие проекты сразу ложатся на сервер, а не в
браузер.

**Оба варианта сервера — один код.** Облачный: Supabase, платный или
бесплатный, если влезает. Физический: Supabase на своём компьютере в цеху
(Docker, открытый код). REST API и `tools/supabase/schema.sql` одни и те
же.

Для физического сервера нужен HTTPS (домен и сертификат или Cloudflare
Tunnel): без защищённого соединения браузер не даёт Web Locks, и запись в
ERP выключается. Однажды проверить этап 4 и на локальном `supabase start`,
а не только на облаке.

Чек-лист, по шагам, с владельцем:

1. Сохранить отчёты испытаний (`~/.glass-erp-walk/perf`), если нужны.
2. **Боевой сервер.** Совет: физический в цеху — интернет с перебоями.
   Или новый проект Supabase (например, `glass-erp-shop`).
   - `schema.sql`, новые входы, HTTPS.
   - Приложение раздаёт сам сервер, а не GitHub Pages.
   - Доступ — из сети цеха.
   - Ночная копия вне цеха (`pg_dump` или Export v2).
3. **Загрузка проектов прошлых лет** — если владелец решит; откуда и как —
   отдельное задание, только по его слову.
   - Файл в формате Export v2 грузить не через браузер, а инструментом на
     Mac владельца (например, `tools/supabase/upload.js`; ключ
     service_role только там, в Git никогда).
   - Старое сразу в архиве по правилам этапа 3.
4. **Сверка с источником:** число заказов и суммы по годам, долги
   клиентов, выборочно 10 заказов вручную. Расхождения — до начала работы.
5. **Каждое устройство:** Users → Clear database (чипа «TEST DATA» нет) →
   Cloud → подключить к боевому серверу. Скачивается только горячее.
6. Администратор заводит настоящих людей.
7. **Убрать тестовое:**
   - удалить проект `glass-erp-test`;
   - удалить файлы `~/.glass-erp-walk/sim` и `…/perf`;
   - удалить тестовых людей и PIN (`*-people.json`).
