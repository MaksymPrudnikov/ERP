## Задача одной строкой

Сейчас Shipping умеет только «весь заказ готов / весь заказ выдан». Нужно:
готовность по скану, отгрузка частями с packing slip на рейс (много заказов и
бэкордеров одного клиента на одних скидах), бэкордер, доставка по плану,
учёт скидов у клиентов и отказ от части позиции с оплатой сделанной работы.

## Решения владельца — не переспрашивать

1. **Packing slip (PS) — один на рейс** к клиенту по одному адресу, внутри —
   разделы по заказам. «Сейчас распечатают 3 отдельно, потому что в системе
   нет возможности; если будет — почему нет». Номер `PS-0001`, штрихкод
   Code 128 с тем же текстом. **Цен на PS нет.**
2. **К PS — лист на каждый скид** (Letter): код скида крупно, клиент, адрес,
   номер PS, заказы и PO, что на скиде лежит (строка, размер, Makeup, штук).
3. **Погрузка: офис заранее, скан проверяет.** Офис собирает отгрузку из Ready
   и печатает PS; на станции SHIP грузчик сканирует скиды; скид не из этой
   отгрузки или чужого клиента — красным со звуком, без окон.
4. **Бэкордер — тот же заказ.** Статус «Partially shipped»; на PS у каждой
   строки: Ordered / Before / Now / Back order.
5. **Счёт — за весь заказ**, по термам кредита и депозита: «ничего по
   отдельности». **Net — с момента, как клиент получил ВСЕ юниты** (последняя
   доставка или самовывоз). PS — не счёт.
6. **Ready — сам по скану на SHIPR.** Кнопка Mark ready не нужна. Частично
   готовый заказ виден как «18 / 20 ready».
7. **Delivered — скан подписанного PS в офисе.** Водитель привозит
   подписанный лист, офис сканирует штрихкод; имя принявшего — по желанию.
8. **Свои машины, нужен план на день**: дата, машина, водитель, остановки по
   порядку, лист рейса водителю.
9. **Скиды**: «бывает, скид остаётся и нам на замену дают другие; бывает,
   оставляем и забираем через какое-то количество дней». Наш скид с кодом
   возвращается сканом; чужой — заводим новым кодом с этикеткой, а наш,
   оставшийся у клиента, списывается как обменянный.
10. **Skid Deposit — как есть**: сумма в заказе руками, «только для новых или
    редких клиентов». Учёт скидов денег не касается.
11. **Чужое стекло на скиде** (SHIPR): предупреждение цветом и звуком, скан
    пишется, работа не стоит.
12. **Отказ от части позиции** — «как сейчас — 100 процентов неправильно».
    Владелец: «линия 1 имеет 21 панель, клиент спустя 2 дня говорит: я не хочу
    6 из них — мы нажимаем Unbatch, меняем количество; за те, что только
    порезались, клиента чарджим только за стекло — добавляем новую линию и
    чарджим только за тот сервис, который был проделан; если стекло было
    закалено — он платит за весь путь и закалку; если это IGU — не платит за
    распорку и силикон».
13. **Стекло отменённых юнитов — по решению клиента**: «как правило выкидываем,
    но иногда клиент может забрать; если стекло не закалено — клиент может
    забрать или попросить использовать для другого заказа».
14. **Отмена — без отдельного бланка**: клиент получает обновлённые Proforma и
    Order confirmation. Не порезано — $0, и за стекло тоже; порезано — платит
    за само стекло; отдельной платы за резку нет.
15. **Какие юниты на Hold и в отмену** выбирает система: сначала
    непорезанные; если все порезаны — те, что прошли меньше работ до закалки
    (между равными — любые); закалённые — последними («после закалки уже
    ничего не изменить, ни в сток, никуда»); собранные IGU — в самом конце.
16. **Порядок работ: сначала отгрузки и PS.**

Ограничение: данные пока в `localStorage` одного компьютера. Телефон водителя
ничего не отмечает — всё через офис и станции.

## Модель данных (для всех PR)

- **Отгружаемая единица — юнит позиции**: (заказ, строка, номер юнита
  1…qty). IGU и ламинат — по U-, одинарное — по G-. **Готов** — все его
  стёкла ждут на станции отгрузки (прошли станцию готовности). Скид юнита —
  `on` последнего скана. Юниты одной позиции взаимозаменяемы.
- **`DB.shipment`** (+ `DB.shipmentSeq`), одна запись — один PS:
  `{id, number:'PS-0001', customerId, method:'delivery'|'pickup',
  shipTo:{label, addressee, address1, address2, address3, postalCode,
  contact, phone}, date:'YYYY-MM-DD',
  status:'planned'|'shipped'|'delivered'|'cancelled',
  items:[{orderId, lineId, unit, label, skid}],
  extras:[{orderId, extraId, qty}],
  createdAt, createdBy, shippedAt, shippedBy, deliveredAt, receivedBy, note}`.
  `shipTo` — снимок: правка адреса клиента старый PS не меняет. После
  `shipped` состав не меняется. PR 3 добавит `truckId, driverId, stop`.
- **Бэкордер не хранится**: заказано (qty − отменённые) − отгружено.
- **Статус заказа `shipping`** — между `ready` и `done`. Подпись «Partially
  shipped», если остался бэкордер, иначе «Shipped». `done` ставится сам, когда
  все юниты и товары склада получены (delivered) или отменены; дата `done` —
  день последнего получения (это и есть начало Net). `fulfilledVia` — по
  последней отгрузке. Шаг «Partially shipped» в шкале — только если он был.
- Старые данные: заказы `done` / `closed` без отгрузок считаются отгруженными
  целиком; бэкордера у них нет.

## PR 1 — Отгрузки и packing slip (офис)

**Ready сам.** Пересчёт статуса заказа — в той же команде, что его меняет:
скан станции готовности и его Undo, отмена юнитов (PR 5), Verify складского
заказа (стекла нет → сразу Ready, как сейчас). Кнопку Mark ready убрать.
Вкладка Awaiting readiness остаётся списком, плюс колонка «Ready x / y».

**Вкладка Ready — по клиентам.** У клиента: скиды с содержимым («SL-5 · 24
units: 76010 ×4, 76015 ×20»), юниты без скида, по заказам «ready / not ready /
back order», адрес доставки по умолчанию. Выбор — скидом целиком, заказом или
строкой (количеством). Скид с юнитами двух клиентов показывать у обоих, в PS
идут только юниты своего клиента.

**Create packing slip** — выбор только одного клиента:
- адрес: адреса delivery клиента, вписать адрес объекта, или Pickup;
- дата; количество по строкам (по умолчанию — всё готовое из выбора); товары
  склада (по умолчанию — неотгруженные, можно снять);
- до записи — `salesTransitionChecks(o,'done')` по каждому заказу PS
  (cash: долг → Take payment / обойти; credit: Hold, просрочка, лимит), как
  в `optimizationRunOrders`;
- создаётся PS `planned`; в журнал заказа: «Packing slip PS-0012 created».

**Вкладка Shipments** — таблица PS (номер, клиент, дата, способ, скиды, юниты,
статус) в стиле таблиц Sales (фильтры колонок, без общего поиска):
- **Print** — PS и лист на каждый скид одним окном печати, Letter;
- **Shipped** — кнопкой (в PR 2 — сам после погрузки сканом);
- поле скана «Signed packing slip» всегда в фокусе на вкладке: скан PS-номера
  → Delivered (Picked up у самовывоза), поле Received by — по желанию;
  кнопка Delivered — запасной путь;
- отмена `planned` — юниты вернулись в Ready; откат `shipped` / `delivered` —
  с подтверждением и записью в журнал.

**Packing slip** (картинка владельцу показана 5.10): шапка — компания, PS-номер
крупно, штрихкод, дата; Ship to (адрес, контакт на объекте), способ; разделы

**Вкладка Backorders** — заказы в `shipping` с остатком: по строкам

## PR 5 — Hold units и Cancel units (Sales)

Картинка владельцу показана 5.10: меню строки → Hold → строка на Hold →
Cancel → заказ после.

**Меню строки** (`line-hold.js`) у строки в цеху: **Hold units…**,
**Cancel units…**, **Release hold**. У строки вне батча — как сейчас.

**Hold units**: число и причина. Юниты выбирает система (решение 15) →
`line.heldUnits [{unit, at, reason}]`. Их стёкла на любой станции — красное
«HOLD · set aside» (как `g.l.onHold` в `stationCheck`; скан пишется). В Ready
и PS не попадают. В заказе под строкой красная полоса «6 units on hold ·
причина · дата» с Release / Cancel units. Раскрой не трогаем: порезанное с
листа просто откладывают.

**Cancel units**: число (по умолчанию — юниты на Hold) и причина. Окно по
каждому юниту: где он (по сканам) и сколько стоит:
- не порезан — $0, и за стекло тоже;
- лайт порезан — цена отожжённого стекла (`salePriceAnnealed` × площадь);
- лайт прошёл HEAT — цена закалённого;
- работы строки — только станций, которые это стекло прошло;
- камера (распорка, герметик) и плёнка ламината — только если юнит собран;
- надбавки Triple / Large — тем же процентом от этой суммы;
- собранный юнит — полная цена.

Итог — строка заказа «Cancelled N units · line 1 · work done»
(`o.cancellations[] {id, at, by, lineId, units, pieces, reason, charge,
chargeOverride}`); цену продавец может поправить. Она входит в итоги заказа
(`salesOrderCommercialTotals`), в Proforma и Order confirmation, в баланс.

**Строка**: `line.cancelledUnits` — qty не трогать, номера стёкол не
перекладывать; заказано = qty − отменённые. На бланках: «15 · 6 cancelled».
Поля добавить в синхронизацию с черновиком (`salesSyncRecordLifecycle`) и в
сравнение замка строки — так, чтобы правка их через окно не считалась
«изменением строки из батча».

**Стекло** каждого порезанного юнита: **Scrap** (по умолчанию) / **Customer
takes** (сразу готово к отгрузке, едет со следующим PS как «cancelled,

## Каждый PR

- Интерфейс только по-английски, подсказки — несколько слов.
- `npm run build:web`, закоммитить `src/index.html`; `dist/` не коммитить.
- `npm run test:snap` целиком, `-- --dist` перед PR; `test/audit-fixes.js`
  (walk-in, две вкладки) зелёный.
- Число проверок в первом абзаце `README.md`; новый раздел сверху
  `docs/GLASS_ERP_HANDOFF.md` и версия в четырёх местах (тест `docs.js`);
  новые файлы — в `КАРТА-ПРОЕКТА.md`.
- Картинки «сейчас / после» владельцу на его выгрузке:
  `npm run shot -- --data latest --tab shipping`; PS и листы скидов —
  `--print --pdf`; станции — `--eval "location.hash='#station=SHIP'"`.
- PR честный (`docs/ДЛЯ_ЧАТГПТ.md`). Сливает владелец. После слияния
  последнего PR это задание удалить.
