# Инструкция для ИИ, который пишет код для этого проекта

Отдай этот файл целиком ChatGPT (или любой другой модели) **перед** тем, как просить её что-то сделать.
Он написан так, чтобы код приходил сразу пригодным к заливке, без переделок.

---

## 0. Одно правило важнее всех остальных

**Не переписывай проект. Меняй минимальный связный набор исходных файлов.**

Система собрана из 50 маленьких модулей именно для того, чтобы чинить их точечно.
Обычно это один-два исходника; изменение доменной модели может потребовать ещё UI,
CSS и regression test. Ответ вида «вот новый полный HTML-файл» или «вот
переписанный с нуля модуль мунтина» — брак, даже если код хороший: он затирает
чужие правки и ломает связи.

Если у агента есть Git/workspace — он правит исходники в репозитории, собирает
`dist` и показывает пользователю локальный HTML. Если доступа к файлам нет —
тогда отдаёт полное содержимое каждого заменяемого файла.

## 1. Что это за проект

ERP для стекольного производства, заменяет австралийскую систему Spil Glass.
Владелец — не программист, работает через готовые экраны, не через код.
Масштаб: 10–100 заказов в день, один-два цеха.

Репозиторий: https://github.com/MaksymPrudnikov/ERP
Живая версия: https://maksymprudnikov.github.io/ERP/
Управляющий документ проекта: `docs/GLASS_ERP_HANDOFF.md` — там вся история решений.

**Актуальная проверенная точка 30 августа 2026:** Sales Makeup refinement влит
через PR #28 `codex/laminated-frit-type`; 222 теста по `src` и 222 по собранному
`dist`. **Устарело — см. ниже актуальную точку 2 сентября 2026.** Перед новой
задачей синхронизировать `main` и прочитать верхний раздел
handoff. Следующая отдельная задача по просьбе владельца — переработка вставки
строк из Excel; не смешивать её с Laminated.

## 2. Технические рамки (нарушение = код не заработает)

Приложение — **не React и не Node runtime**. Это набор обычных браузерных
скриптов, которые подключаются подряд тегами `<script src>` и собираются в один
HTML-файл. Node используется только как инструмент сборки и Playwright-тестов.

**Нельзя:**
- `import` / `export` / ES-модули — файлы подключаются как classic scripts, `import` бросит ошибку
- `require()` — в браузере его нет
- TypeScript, JSX, декораторы, аннотации типов
- npm-пакеты, CDN-ссылки, любые внешние зависимости — файл обязан работать при открытии с диска
- сборщики: webpack, vite, esbuild, babel
- `<link>` или `fetch` на внешние адреса

**Можно и нужно:**
- обычный ES5/ES6 JavaScript в глобальной области видимости
- `function имя(){}` и `const/let/var` на верхнем уровне файла — они видны всем остальным файлам
- шаблонные строки, стрелочные функции, `Array.map/filter/reduce` — это всё поддерживается

**Порядок подключения важен.** Файл выполняется в порядке из `build/manifest.json`:
core → modules/shape → modules/muntin → erp → `erp/storage.js` последним.
Обращаться к функции из файла, который идёт позже, можно только **внутри функции**
(она вызовется потом), но не на верхнем уровне при загрузке.

## 4. Контракты — их нарушать нельзя

Модули соединяются только через эти две функции. Всё остальное внутри модуля можно менять свободно.

```js
ShapeModule.compute(shapeDef)
// вход:  {id, name, w:'48', h:'36', smart:{elbowsOn, A, B, C, corners, extraEdges}}
// выход: {valid:true,  width, height, area, points:[[x,y],…], segs, base, warns, line, geometry}
//        {valid:false, reason:'текст ошибки', errors:[…]}

MuntinModule.compute(shape, muntinDef)
// вход:  shape — объект фигуры (тот же, что уходит в ShapeModule.compute)
//        muntinDef — {id, name, shapeId, muntin:{enabled, productId, flipped, layout, production}}
// выход: {valid:true,  geo, M, count, totalLengthIn, verticalSegments, horizontalSegments}
//        {valid:false, reason:'текст ошибки'}
```

### Четыре запрета

1. **Shape — единственный источник размеров стекла.**
   В Muntinbar **не добавлять** собственные Width/Height, не считать габарит внутри мунтина.
   Мунтин получает уже готовую фигуру и работает по её реальному периметру.
   Второй источник геометрии = расхождение размеров = брак в цеху.
   Это проверяется автоматическим тестом.

2. **Не переписывать геометрию v4.5 «заодно».**
   Расчёты Shape и Muntin перенесены дословно из рабочего конфигуратора Glass Configurator v4.5.
   Улучшать их можно только отдельной задачей, с явной просьбой владельца, и с обновлением
   эталонных чисел в тестах. Тихо «оптимизировать» — нельзя.

3. **Модуль не знает про деньги.**
   В `modules/shape/*` и `modules/muntin/*` не должно быть ни цен, ни клиентов, ни заказов.
   Развязка сделана специально, чтобы модуль можно было чинить, тестировать и показывать отдельно.

4. **Не выдумывать протокол обмена с Perfect Cut.**
   Perfect Cut — внешний оптимизатор раскроя. Как именно он подключается, пока не выяснено.
   Не писать формат файла, не имитировать API, кнопку отправки батча оставить неактивной.
   **Уточнение 1 сентября 2026:** оптимизатор раскроя решено писать свой, но
   приступать к нему не раньше БД и настоящих заказов. Порядок работ — БД,
   оптимизатор, станции по логину. Подробности — в верхнем разделе handoff.

## 5. Эталонные числа — по ним проверяется, что ничего не сломалось

Репозиторий гоняет **356** автоматических теста на актуальной точке 2 сентября 2026 (было 222 на 30 августа). Они сохраняют геометрические эталоны, метрический Production Drawing и отдельно проверяют повреждённые данные, импорт/XSS, RU/EN, Sales/Makeups и мобильный viewport. Ключевые значения:

| Проверка | Ожидаемый результат |
|---|---|
| прямоугольник 48 × 36 | площадь 1728 in², 4 точки контура |
| трапеция 48 × 36 при C = 30 (сторона D строится автоматически) | площадь 1584 in², 4 точки |
| угловой блок Single, рёбра E = F = 4 | 6 точек, площадь 1712 in² |
| мунтин 2 верт. × 1 гориз. на этой трапеции | 3 сегмента, длины реза **33 7/64″ · 31 1/8″ · 47 1/8″** |
| тот же мунтин на прямоугольнике | длины **35 1/8″ · 35 1/8″ · 47 1/8″**, форма не считается «shape-adaptive» |
| разные Edge inset X и Y | режим кромки откатывается на `axis` и поднимает флаг `edgeModeForced` |
| сетка производства | ровно 1/16″ |
| разбор размеров | `48 1/2`, `48-1/2` → 48.5; `12abc` → 0 (ошибка, а не 12) |

Если твой код меняет любое из этих чисел — ты сломал перенос v4.5. Либо верни как было,
либо честно напиши в ответе: «внимание, меняется эталон X, нужно обновить тест».

## 6. Если добавляешь НОВЫЙ файл

Файл сам по себе не подключится. Его надо вписать в два места, **в одинаковом порядке**:

1. `build/manifest.json` — массив `scripts`, путь целиком: `"src/modules/muntin/arch.js"`
2. `src/index.html` — тег `<script src="modules/muntin/arch.js"></script>` (путь без `src/`)

Место в списке — рядом с остальными файлами своего модуля, до `index.js` этого модуля.

Если забыть — автоматическая проверка остановит сборку и напишет, какой файл не подключён.
Поэтому **всегда прикладывай к ответу обновлённые `manifest.json` и `index.html`**, если добавил файл.

## 7. В каком виде давать ответ

Если агент работает только через чат без доступа к репозиторию, для каждого файла нужен заголовок с полным путём и следом полный код файла целиком:

> **`src/modules/muntin/clip.js`**
> ```js
> /* весь файл от первой до последней строки */
> ```

**Обязательно:**
- полное содержимое файла, а не фрагмент и не diff — владелец заменяет файлы целиком
- сохранить существующие имена функций, если не просили их менять: на них ссылаются другие модули
- шапку-комментарий в начале файла оставить и обновить (что делает, что на входе, что на выходе)
- комментарии по-русски, как в остальном коде

**Не надо:**
- присылать патчи, diff, «замени строку 42 на …»
- присылать весь проект или весь HTML
- переименовывать функции «для красоты»
- добавлять зависимости, сборщики, тесты на новых фреймворках
- писать «остальной код без изменений» вместо кода

Если агент имеет доступ к Git/workspace, правило другое: сделать точечный patch
в исходниках, прогнать `node build/build.js`, затем `node test/run.js` и
`TARGET=dist node test/run.js`. Для UI сначала дать владельцу локальный HTML на
проверку; создавать ветку и push только после его подтверждения. В Git всегда
отправлять исходники + тесты + собранный `dist`, а не один HTML.

## 8. Что уже решено и не обсуждается

Владелец потратил на эти решения много времени, повторное предложение их пересмотреть — потеря времени.

- Своя система строится **с нуля**, миграция базы Spil отвергнута.
- Оптимизатор раскроя **не пишем** — интеграция с Perfect Cut.
- Бухгалтерию **не переписываем** — остаётся во внешней системе.
- Материал = подложка + толщина + покрытие. Закалка — **не** свойство материала, а процесс.
- Слово «модуль» здесь означает обычный файл с кодом. Это **не** формат Claude Skills.
- Сырой SQL как единственный результат не годится — всё должно открываться как рабочий экран.
