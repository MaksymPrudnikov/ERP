# Ревью `GLASS_ERP_CLAUDE_REVIEW_CANDIDATE.html` → первый коммит

Дата: 16 августа 2026. Что проверялось: файл-кандидат целиком + соответствие handoff.
Как проверялось: прогон в реальном браузере (Chromium), все вкладки, все формы, RU/EN,
битые данные в localStorage, импорт чужого JSON, попытка HTML-инъекции через имя.

**Итог: геометрия Shape/Muntin чистая — регрессий против v4.5 не найдено.
Найдено 7 багов в оболочке и слое ввода. Все исправлены, на каждый есть тест.**

## 1. Белый экран при повреждённом localStorage — критический

**Было:** старт делал `Object.assign(DB, JSON.parse(s))` — в `DB` попадало любое содержимое
ключа `glazing_system_v1`, включая `null` вместо массива. Дальше `normalizeUsers()` падал на
`.forEach`, скрипт умирал, страница оставалась пустой. Ни сообщения, ни возможности починить —
только через DevTools.

**Почему это не теория:** тот же ключ `glazing_system_v1` использовала предыдущая оболочка
прототипа с другой структурой данных. Открыть новый файл в том же браузере — и данные уже чужие.

**Стало:** `mergeState()` берёт только известные ключи и только правильного типа,
`normalizeDB()` чинит типы, `boot()` при любой ошибке откатывается на дефолты и пишет
предупреждение в консоль. Приложение больше не может не запуститься.

`src/erp/storage.js` · тесты: `битый localStorage не даёт белый экран`, `нечитаемый localStorage не роняет старт`

## 2. `48-1/2` молча превращалось в `48` — критический для расчёта

**Было:** два разных парсера размеров на одном экране.

| Ввод | Width / Height (`inch`) | Сторона C (`fabParseDimStrict`) |
|---|---|---|
| `48 1/2` (пробел) | 48.5 | 48.5 |
| `48-1/2` (дефис) | **48** ← дробь потеряна | 48.5 |
| `12abc` | **12** ← мусор принят | ошибка |

То есть ширину `48-1/2″` система считала как `48″` — без единого предупреждения, и дальше
эта ошибка ехала в контур, в раскрой мунтина и в длины баров. При этом та же строка,
введённая в поле C, читалась правильно. Классический случай, когда деталь режется не того размера.

**Стало:** один строгий парсер на всё. Непонятный ввод = 0 и ловится валидацией
(«Enter valid width and height»), а не считается тихо.

`src/core/dim.js` · тесты: `inch("48-1/2") == strict parser`, `inch("12abc") отбрасывается`

> Это изменение поведения относительно порта v4.5 — сделано отдельным коммитом, откатывается одной командой.

## 3. Уровень станции строкой — станция исчезала из маршрута

**Было:** `station.level` сравнивается строго (`s.level===l.n`). Из импортированного или
руками правленного JSON уровень приезжал строкой `"1"`, и станция молча пропадала из
«Маршрута по уровням» — при этом в таблице выглядела нормально.

**Стало:** `normalizeStations()` приводит `level` и габариты к числу или `null` при каждой загрузке и импорте.

`src/erp/data.js` · тесты: `level строкой приводится к числу`, `станция попадает в маршрут`

## 4. Переименование номера уровня осиротляло станции

**Было:** удалить уровень со станциями запрещено (правильно), а сменить его **номер** — можно.
После смены `1 → 9` станция `CUT1` осталась с `level: 1`, которого больше нет. Защита от
удаления есть, защиты от переименования нет.

**Стало:** станции едут за уровнем; `DB.level` держится отсортированным при записи, а не в рендере.

`src/erp/views/production.js` · тест: `переименование номера уровня не осиротляет станции`

## 5. RU/EN переводил данные пользователя, а не только интерфейс

**Было:** переводчик обходил **все** текстовые узлы. Станция или сотрудник с именем
«Закалка» в EN превращались в «Tempering» — менялись сами данные на экране, а не подписи.

**Стало:** значения из базы помечаются `data-raw` и не переводятся никогда.
Исключение — строки, засеянные нами (дефолтный каталог станций и уровней): они переводятся,
чтобы в EN каталог по умолчанию не был русским. Как только пользователь переименует запись,
её значение перестаёт совпадать с засеянным и дальше остаётся как введено.

`src/erp/nav.js`, `src/erp/i18n.js` · тест: `данные пользователя не переводятся`

## Проверено и признано корректным

- **Геометрия Shape → контур → Muntin.** Эталонные числа зафиксированы в тестах: трапеция

- **Shape — единственный источник размеров.** В Muntinbar нет своих Width/Height. Проверяется тестом,
  чтобы это не завезли обратно.
- **Разные `edge inset X/Y`** корректно откатываются на `axis` с явным флагом и объяснением на экране.

- **CNC1 / FURN1 без уровня** — не проставлены «по догадке», на экране висит вопрос пользователю.

## Осталось на решение (не баги, а незакрытые вопросы)

1. **Сообщения модулей на английском в русском интерфейсе.** `Shape not found`, `Shape is invalid: …`
   приходят из модулей и не переводятся. Это осознанно: модуль не должен знать про язык оболочки.
   Правильное место для перевода — оболочка, по коду ошибки. Пока кодов ошибок нет.
2. **`id` фигуры/раскладки = `'s' + Date.now()`.** Две записи, созданные в одну миллисекунду,
   получат одинаковый id. На реальном ритме работы недостижимо, в БД заменится на серверный id.
3. **Журнала событий нет.** Handoff требует писать событие на каждое действие в каждом модуле.
   В прототипе не реализовано — это отдельный слой ядра, не правка.
4. **Экраны Inventory / Purchasing / Shipping / Finance** видны в меню как план, экранов нет.
5. **Модель материалов и цены** (миграции 01–05, прототип `glass_erp_v3.html`) в новую оболочку
   ещё не перенесена — остаётся справочным источником.
