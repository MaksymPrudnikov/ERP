# Архитектурное предложение: Web-first для GLASS ERP

Дата: 2026-09-04

## Короткий вывод

Основным продуктом следует сделать браузерное web-приложение, устанавливаемое как PWA при необходимости. Полноценную desktop-версию пока не делать.

Единый `dist/GLASS_ERP.html` оставить как дополнительный standalone-дистрибутив для передачи, аварийного запуска и сценариев без сервера. В обычной разработке и в feature-ветках generated `dist` не должен быть главным объектом работы.

## Исходная ситуация

- Исходники уже разделены по модулям в `src/`.
- Текущий standalone HTML занимает примерно 1,5 МБ без сжатия.
- Основной размер дают интерфейс формы фигур, каталог стекла, переводы и CSS; это не означает, что приложение надо переписывать.
- В проекте уже есть проверка воспроизводимости сборки: одинаковые исходники с LF и CRLF дают одинаковый результат.
- Функциональные и dist-тесты проходят: 383/383.

Размер standalone-файла сейчас не является критической проблемой для браузера. Главный риск — постоянные конфликты и лишние изменения generated-файла при работе с Git.

## Что считаем обязательным

### Уже сделано и должно остаться обязательным

1. Сборка только из `src/`.
2. Нормализация переводов строк перед хешированием и объединением файлов.
3. Проверка manifest, синтаксиса, воспроизводимости и функциональных тестов в CI.
4. Запрет ручного редактирования `dist/GLASS_ERP.html`.

### Следующий обязательный этап

Сделать две цели сборки:

- `build:web` — многофайловая версия для обычного запуска в браузере;
- `build:standalone` — единый HTML для offline/portable-сценариев.

Для `build:web` желательно использовать хешированные имена ассетов, например `assets/app.<hash>.js`, чтобы браузер безопасно кэшировал неизменившиеся файлы.

## Предлагаемый поток работы

```text
src → тесты → build:web → браузер/PWA
          └→ build:standalone → GitHub Release или CI artifact
```

Рабочий процесс:

1. Разработчик меняет только `src/` и тесты.
2. Pull Request запускает тесты и обе сборки.
3. Pull Request не обязан содержать сгенерированный standalone-файл.
4. После merge CI публикует web-артефакт.
5. При создании тега CI прикладывает standalone HTML к GitHub Release.

Перевод generated `dist` из обычного PR-потока нужно делать после того, как `build:web` будет проверен на полном наборе тестов. Не стоит одновременно менять архитектуру сборки и функциональность ERP.

## Производственные экраны и быстрый barcode flow

Производство должно получать отдельные лёгкие экраны/entry points, например
`production` и `optimizer`, а не загружать весь офисный ERP-интерфейс. Это не
отдельная копия приложения для каждого сотрудника: один и тот же экран
работает с контекстом станции и роли, а общие доменные модули остаются едиными.

Целевое требование для имеющихся Bluetooth-сканеров — до 1 секунды от скана
до подтверждения операции на экране при нормальной сети (контроль: 95-й
перцентиль). Сканер работает как HID-клавиатура и завершает код `Enter`; один
запрос выполняет индексированный lookup и запись события в транзакции.

Поток оптимизации: проверенные строки → подтверждённый `optimization_batch`
со снимком → отдельный экран по `batchId` → расчёт в `Web Worker` или серверной
фоновой задаче → результат и статус в Supabase/PostgreSQL. В URL передаётся
только ID, не копия заказа.

Производственные операции должны быть append-only событиями с
`idempotency_key`, станцией, оператором и временем. При обрыве сети PWA пишет
событие в IndexedDB и досылает его после восстановления; серверная база остаётся
источником правды. Отдельное окно уменьшает UI/bundle-нагрузку, но тяжёлый
расчёт всё равно обязан быть вынесен из главного потока.

## Этапы развития

### Этап 1 — стабилизация сборки

- Оставить текущую проверку воспроизводимости.
- Добавить `build:web`.
- Добавить CI artifact для web-сборки.
- Документировать локальный запуск через dev-сервер.
- После проверки перестать использовать generated HTML как место ручной работы.

### Этап 2 — удобное браузерное приложение

- Добавить PWA manifest и service worker.
- Кэшировать приложение для повторного offline-запуска.
- Загружать крупные разделы по требованию, если это даст измеримый эффект.
- Вынести крупные каталоги и переводы в отдельные JSON только там, где это не ломает offline-сценарий.

### Этап 3 — совместная ERP

Когда потребуется работа нескольких сотрудников и устройств одновременно:

- добавить API;
- вынести общие данные из `localStorage` в серверную базу данных;
- добавить пользователей, роли, авторизацию, резервное копирование и журнал изменений.

Это отдельный этап. PWA сама по себе не решает проблему общей базы данных.

### Этап 4 — desktop-оболочка только при необходимости

Рассматривать Tauri (или другой thin wrapper) только если появится подтверждённая потребность в прямом доступе к USB/COM, станкам, локальным папкам или специфическим принтерам. В desktop-оболочку следует упаковывать ту же web-версию, а не создавать вторую реализацию ERP.

## Что сейчас не нужно делать

- переписывать проект на другой framework;
- делать Electron/Tauri только из-за размера HTML;
- удалять standalone-режим до готовности web-сборки;
- дробить файлы только ради уменьшения числа строк без измерений;
- строить backend до появления требования о совместной работе и центральных данных.

## Критерии успеха следующего архитектурного PR

- web-версия функционально проходит тот же набор тестов, что и standalone;
- повторная сборка из одинакового commit даёт одинаковые хеши;
- PR с изменением исходного модуля не требует ручного разрешения конфликтов в большом generated HTML;
- standalone-файл по-прежнему можно получить одной командой и скачать из Release;
- документирован способ локального запуска и способ публикации версии.

## Вопрос Claude для независимой проверки

```text
Мы развиваем GLASS ERP. Сейчас исходники модульные (`src/`), а для распространения собирается один `dist/GLASS_ERP.html` примерно 1,5 МБ. В проекте уже исправлена воспроизводимость сборки (LF/CRLF), есть CI и 383 функциональных теста.

Предлагаемая стратегия:

1. Основной продукт — browser web app, в будущем PWA.
2. Добавить многофайловый `build:web` с кэшируемыми JS/CSS/JSON.
3. Оставить `build:standalone` как offline/portable-дистрибутив.
4. Не держать generated standalone HTML в обычном потоке feature-веток; публиковать его из CI/GitHub Release.
5. Backend/API/БД добавлять, когда появится многопользовательская работа.
6. Tauri/desktop делать только при подтверждённой интеграции со станками, USB/COM или локальными принтерами.

Проверь эту стратегию как независимый технический ревьюер:

- согласен ли ты с web-first/PWA вместо немедленной desktop-версии;
- есть ли критические риски у двух целей сборки (web и standalone);
- в какой момент нужен code splitting и вынос каталогов/переводов в JSON;
- когда backend становится обязательным;
- какие конкретные шаги и критерии готовности ты бы добавил;
- что из предложенного ты бы изменил или не делал.

Дай ответ с приоритетами: критично сейчас, важно следующим этапом, можно отложить.
```
