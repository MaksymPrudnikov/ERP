## 1. Контекст и рамки проекта

- **Кто:** владелец стекольного производства, использует Spil Glass ERP (Австралия), недоволен архитектурой типов стекла в текущей БД — считает её изначально неверной.
- **Цель:** не надстройка над Spil, а полная замена. Spil в итоге отключается совсем.
- **Текущий масштаб:** 10–100 заказов в день максимум, один-два цеха. При этом 18 авг 2026 пользователь одобрил расширенный целевой контур без архитектурного тупика: CPQ, MES/APS, полная genealogy, QMS, maintenance/energy, порталы, BI и будущий мультизавод. Это направление, а не требование внедрить всю сложность в первой фазе.
- **Роль разработчика:** ИИ (Claude) пишет код блоками/модулями постепенно. Пользователь не программист, работает через визуальную итерацию — смотрит готовый экран, а не код или SQL напрямую.
- **Развёртывание:** предпочтение — облако. Локальная копия на ПК допустима на старте, перенос на сервер позже. Часть операций (печать этикеток, выгрузка на станки) физически требует локального агента в цеху — облако до принтера/станка не достаёт.
- **Бюджет времени:** честная оценка полной замены — 15–25 месяцев, по фазам, каждая фаза даёт самостоятельную пользу.

### Ключевой принцип работы с пользователем
Пользователь учится через **визуальную итерацию**, не через код или SQL в чате. Он явно раскритиковал подход "получать сырые .sql файлы" — не может их использовать напрямую. **Каждая часть системы должна поставляться как рабочий HTML/браузерный прототип**, который открывается двойным кликом, без установки, без сервера. Сырой SQL — это внутренний рабочий материал для будущего переноса на сервер, не то, что показывается пользователю.

## 2. Что уже отвергнуто и почему (не предлагать снова)

| Отвергнуто | Причина |
|---|---|
| Миграция/патч текущей БД Spil | Архитектура типов стекла ошибочна с самого начала (закалка была зашита в тип стекла). Решено строить с нуля |
| Импорт клиентов Excel'ем на старте | Отложено — сначала один тестовый клиент + один тестовый тип стекла, клиенты грузятся позже |
| SQL-файлы как основной способ показать прогресс | Пользователь прямо сказал "зачем ты мне даёшь файлы SQL" — нужен рабочий интерфейс |
| Multi-select `<select multiple>` для выбора листов | Непонятно пользователю без Ctrl+клик — заменено на чекбоксы |
| Read-only прототип без возможности редактировать/удалять записи | Пользователь спросил "как потом манипулировать данными" — все сущности получили полный CRUD (добавить/изменить/удалить) с защитой от удаления используемых записей |
| Плоский список типов стекла ("6MM CLR TEMP" как одна строка) | Смешивает подложку, толщину, покрытие и обработку в одну строку — теряет связи, раздувается на сотни строк, не выводит остаток/маршрут/себестоимость |
| Группировка модулей "как удобно вводить" (материалы+покрытия+станки вперемешку) | Пользователь потребовал группировку **по бизнес-домену/владению**: склад/закупки/продажи/производство/отгрузка/финансы — каждый модуль отдельный, со своим отчётом, но связанный через ссылки |
| Хранить весь функционал Glass Configurator в одном большом файле | Частично готовые функции (мунтин ~80%, shape ~40%) мешают друг другу при правках. Решено: каждая специфическая способность — отдельный модуль кода с чётким входом/выходом, подключаемый к сервису (раздел 3, "Декомпозиция на независимые модули") |
| Слово "skill" в значении Claude Skill (SKILL.md/.skill) для этих модулей | Пользователь подтвердил — имел в виду обычный модуль кода, не формат Claude Skills. Не путать |
| **Глобальная Configuration Library** (общая на всю систему библиотека конфигураций стеклопакета) | Пользователь начал кликать конфигурации и увидел, что их сотни и тысячи. Комбинаторика делает библиотеку невозможной: по текущему сид-каталогу один Double = `(16 стекло × 3 закалки) × (8 spacer × 2 газа × 3 × 3 герметика) × (16 × 3)` = **331 776 сочетаний**, и это пока только 6 мм. С реальными толщинами, поверхностью покрытия, Frit, Spandrel, Laminated и Triple счёт идёт на миллионы. Заранее создать и назвать их нельзя — оператор утонет в поиске и наплодит дублей. Это та же болезнь, что и плоский список типов стекла «6MM CLR TEMP», только этажом выше. **Решение:** Makeup живёт внутри своего Sales Order и легко меняется; общая личность одинаковых пирогов даётся не хранимым каталогом, а вычисляемым fingerprint из id (см. раздел 5.4) |

## 3. Архитектурные решения (стек, платформа)

- **База данных:** PostgreSQL (Supabase или Neon).
- **Бэкенд + фронт:** TypeScript, Next.js. Монолит — не микросервисы, масштаб (10–100 заказов/день) не требует такой сложности.
- **Оптимизатор раскроя: НЕ пишем сами.** Решено интегрироваться с уже используемым **Perfect Cut** (R.O. SRL / Operations Research, perfectcut.glass) вместо разработки своего движка нестинга — это снимает самый тяжёлый и рискованный кусок фазы 3.
  - У пользователя только базовый Perfect Cut, без модулей Perfect Label / Perfect Code / Perfect Stock.
  - Печать стикеров/этикеток уже решена — Perfect Cut печатает их сам на принтере (TCL/TSC). Наш локальный агент печать этикеток НЕ обслуживает.
  - Трекинг детали по станциям цеха и учёт остатков/обрези по-прежнему наши — Perfect Code (штрихкоды) и Perfect Stock (остатки) у пользователя не куплены.
  - **Механизм обмена ещё не подтверждён.** Со слов пользователя: "по нажатии кнопки Perfect Cut получает доступ к батчу" — похоже на прямое подключение к БД Spil (SQL Server) или настроенный коннектор R.O. SRL под Spil, а не на ручной файловый экспорт. План: пользователь посмотрит настройки подключения в Perfect Cut (DSN/строка подключения к Spil) и/или спросит у R.O. SRL, как именно настроен этот коннектор — прямая БД, ODBC или файл, и в каком формате. До получения этой информации формат обмена не проектируется — угадывать его бессмысленно.
  - Локальный агент в цеху меняет назначение: раньше планировался под печать этикеток + выгрузку DXF на станки, теперь его роль — быть мостом данных между нашей БД и Perfect Cut (передать батч на оптимизацию, забрать результат раскроя обратно для трекинга и учёта остатков).
- **Цеховые терминалы:** PWA с офлайн-очередью (IndexedDB), сканирование пишется локально и досылается при восстановлении сети.
- **Локальный агент в цеху:** отдельный маленький сервис на ПК, его подтверждённая текущая роль — **мост данных между облачной ERP и локальным Perfect Cut**. Печать этикеток оставлена Perfect Cut; формат/механизм обмена пока не проектировать до получения реальных настроек коннектора Spil ↔ Perfect Cut. Выгрузка на другие станки может потребовать локальный компонент позже, но конкретный протокол не придумывать заранее.
- **Хостинг:** Vercel/Fly + managed Postgres + ночной дамп на локальный NAS как резервная копия (не второй источник правды).
- **Переезд на сервер отложен осознанно (решение пользователя, 21 авг 2026).** Дословно: «пока хранить только в браузере для тестового образца на поклацать». Вместо переезда пользователь заказал **экран работы с базой** — чтобы своими руками полазить по данным и сказать, чего в модели не хватает и что лишнее. То есть Postgres не раньше, чем модель будет им же принята на прототипе. Признак, что тянуть больше нельзя, остаётся прежним: двум людям нужно работать одновременно, либо потеря браузерных данных станет неприемлемой.
- **Бухгалтерия НЕ переписывается.** AR/AP, GL, payroll, tax, cash book, fixed assets остаются во внешней системе (QuickBooks/Xero/Sage). Своя ERP только выставляет счёт и передаёт данные наружу. Это решение экономит ~год работы и снимает регуляторный риск.

### Прототипирование — текущий подход
Каждый модуль сначала строится как **самодостаточный HTML-файл** (inline CSS/JS, без зависимостей, открывается локально), с:
- Полным CRUD по всем сущностям (добавить / изменить / удалить с защитой от удаления используемых записей)
- Экспортом/импортом состояния в JSON (кнопки в шапке) — так пользователь сохраняет свою работу между сессиями и присылает её обратно для переноса в реальную БД
- Автосохранением в localStorage браузера
- Валидацией на вводе (обязательные поля, дубликаты, диапазоны)
- Живыми расчётами (проверка маршрута, цена детали) — не просто справочники, а рабочая логика

Когда модель устаканится на прототипе — те же самые экраны переезжают на реальный Next.js + Postgres, меняется только источник данных.

### Декомпозиция на независимые модули (решение от авг 2026)

Пользователь сформулировал принцип: не писать всю функциональность в один файл/модуль, а разбивать каждую специфическую способность (требующую своей геометрии, чертежей, расчётов) на **отдельный модуль кода** — и уже потом подключать его к кнопке или сервису внутри системы.

**Важно про терминологию:** пользователь употребил слово "skill", но явно подтвердил (авг 2026, при уточнении) — имеется в виду **обычный программный модуль**, НЕ формат Claude Skill (SKILL.md/.skill). Не путать эти два понятия при дальнейшей работе. В документе и коде использовать слово "модуль", не "skill", чтобы не создавать путаницу с системой Skills этой платформы.

**Технический контракт модуля:**
- Один файл/папка на одну способность (например `muntin.js`, `free-shape.js`).
- Чёткий вход/выход: модуль получает данные (например размеры камеры, параметры сетки) и возвращает результат (геометрия, DXF-сегменты, BOM) — без обращения к остальной системе напрямую.
- Модуль не знает про цены, клиентов и заказы — эта развязка инженерной логики (геометрия/DXF) от бизнес-логики (цена/клиент) сделана специально: так модуль можно чинить, тестировать и потенциально показать/предложить/продать отдельно, не утаскивая за собой закрытые бизнes-данные.
- Точка подключения — сущность `service` из модели данных (раздел 4.2): у сервиса типа "мунтин" может быть привязан конкретный модуль-калькулятор. Это совпадает с уже существующей моделью услуг в ERP, отдельного нового механизма подключения выдумывать не нужно.

**Решение по конкретным функциям Glass Configurator (авг 2026):** Muntinbar и Shape **переносятся из существующего Configurator, а не переписываются с нуля**. Для текущего ERP-кандидата уже подключена реальная логика **Smart-Shape / Advanced из v4.5** и shape-adaptive **Muntin Production**. При переносе не исправлять известные геометрические баги попутно: сначала сохранить существующее поведение и контракт, затем чинить внутри изолированного модуля отдельными изменениями.

**Критическая связь Shape → Muntin:** Shape является единственным источником размеров и контура детали. Пользователь сначала создаёт/выбирает Shape (Width/Height + Advanced geometry), затем Muntinbar выбирает этот Shape и рассчитывает сетку/длины баров по его реальному контуру. **Не добавлять отдельные Width/Height в Muntinbar** — это создаст второй источник геометрии и риск расхождения.

### Workflow разработки: коммиты напрямую из облака (решение от авг 2026)

## 4. Ядро модели данных — материалы и стекло

### 4.1 Главный принцип: разделение осей
**Материал = подложка + толщина + покрытие.** Обработка (закалка) НЕ входит в материал — на складе закалённого стекла не бывает, закалку делает сам цех. Название и вес не хранятся полями — вычисляются из связанных таблиц.

Было неправильно: `6MM CLR TEMP` как одна строка справочника.
Стало правильно: `substrate(CLR) + thickness(6mm) + coating(null) → material`, а `treatment(TEMP)` — отдельная сущность, применяется к детали в процессе, не к материалу на складе.

### 4.2 Таблицы (реализованы в SQL-миграциях 01–05)

**`substrate` (подложка)** — тело стекла как сварил завод. БЕЗ толщины, покрытия, обработки.
- `code`, `name`, `family` (clear/low_iron/tinted/patterned/wired/other)
- `tint_colour_code` (FK, обязателен только для tinted)
- `density_kg_m3` (нужен для веса детали: вес = плотность × толщина × площадь)
- `is_temperable`, `is_laminatable`, `is_directional` (узорчатое стекло имеет лицевую сторону)
- `legacy_code` (маппинг на старые артикулы Spil)
- CHECK: tinted обязан иметь tint_colour; wired не может быть temperable (физическое ограничение)

**`coating` (покрытие)** — покрытие как продукт. Номер поверхности (#2, #3, #4) — свойство СЛОЯ ИЗДЕЛИЯ, не покрытия.

> **Уточнение 21 авг 2026 — где живёт surface и где живёт правило.** Пользователь спросил, не должен ли surface попасть в каталог. Не должен, и в оболочке это уже сделано верно: `coatingSurface`, `frit.surface` и `spandrel.surface` хранятся в Makeup на конкретном Lite, диапазон вычисляется из его индекса (`salesPaneSurfaces`: Lite 1 → #1/#2, Lite 2 → #3/#4, Lite 3 → #5/#6), покрытие/Frit/Spandrel имеют независимые surface. Два регрессионных теста это держат. Класть surface в каталог нельзя — «Solarban 70 на #2» и «Solarban 70 на #5» станут разными товарами, и вернётся та же комбинаторика, из-за которой отвергнута Configuration Library.
> **Но правило «где этому покрытию вообще можно стоять» принадлежит продукту, и его в оболочке НЕТ.** `exposure_rule` + `allowed_surfaces` есть в этой модели и в SQL-миграциях, но `glassProduct` в коде их не хранит, а Makeup Builder не проверяет: сегодня можно поставить i89 в камеру, а Solarban внутрь помещения, и никто не остановит. Заведено в Этап 5 плана.
- `coating_type` (low_e/solar_control/reflective/mirror/self_cleaning/anti_reflective/etch)
- `deposition` (pyrolytic твёрдое / sputtered мягкое / chemical / applied)
- `applied_by` (primary_manufacturer / offline_coater / **fabricator** — если наносим сами, это генерирует шаг маршрута, а не позицию закупки)
- `temper_mode` — **тройное состояние, не булево**: `annealed_only` / `temperable` / `temper_required` (свойства раскрываются только после закалки)
- `exposure_rule` (any/cavity_only/exterior_only/interior_only) — рабочий пример: **i89 от Cardinal работает на поверхности #4, внутрь помещения**, а не в камеру, в отличие от всех остальных low-E. Это ловится constraint'ом `coating_mirror_rules` и полем exposure_rule.
- `requires_edge_deletion` + `edge_deletion_width_mm` (согласованы constraint'ом)
- `emissivity`, `shelf_life_days` (мягкие покрытия окисляются, партия имеет срок годности)
- Правило разделения покрытие vs услуга: *если две партии взаимозаменяемы и могут лежать на одной стойке — это покрытие; если задаётся под конкретный заказ (рисунок, %, цвет) — это услуга.* Шелкография = услуга (`line_service`), зеркало/сатин = покрытие (`applied_by = offline_coater`).

**`thickness` (толщина)** — номинал ≠ факт. "6мм" это обозначение, не измерение.
- `nominal_mm`, `imperial_label`, `actual_mm`, `is_verified`
- **Важно:** фактическая толщина в итоге переехала на уровень `material`, а не осталась только в `thickness` — потому что разные линии дают разный факт при одном номинале (6mm Clear = 5.77мм, 6mm LoE-272 = 5.70мм). `material.actual_thickness_mm` перекрывает значение из `thickness.actual_mm`.

**`material`** — единица закупки/склада. `substrate_id + thickness_id + coating_id(nullable) → уникальная связка`. Плюс `actual_thickness_mm`, `thickness_verified`, `legacy_code`.

**`supplier` / `source` (точка поставки)** — отделены друг от друга. Один поставщик может иметь несколько точек поставки с РАЗНОЙ ВАЛЮТОЙ: Vitro Barrie в CAD, Vitro USA в USD, Cardinal USA в USD. Валюта принадлежит точке поставки, не поставщику.

**`sheet_size` (типоразмер листа)** — зависит от ПАРЫ материал+поставщик, не глобален. Vitro продаёт 144×100", Cardinal тот же условный "144" даёт как 144×96". Таблица связи `material_supply_sheet`.

**`treatment` (обработка)** — закалка/HS/отжиг как процесс.
- `is_heat_treated`, `requires_furnace`
- **`can_cut_after`** — главное поле: false у закалки/HS/HST. Отсюда следует весь порядок маршрута: рез, кромка, отверстия — всё ДО печи, размер реза = финальный размер.
- `strength_factor` (HS ≈2x, tempered ≈4x относительно annealed)

**`work_center` (станок/рабочий центр)** — физическое ограничение оборудования.
- `max_width_in`, `max_length_in`, `min_width_in`, `min_thickness_mm`, `max_thickness_mm`
- Заведено: печь закалки `FURN1` (90×150"), кромкообработка `EDGE1`, фацетный станок `BEVEL1` (70×100"), ЧПУ `CNC1` (60×122")
- **ЧПУ — это две разные операции на разных уровнях маршрута** (ответ пользователя, 21 авг 2026): *CNC shape polishing* — **уровень 2** (кромка/полировка), *CNC processing* — notch, radius и прочее — **уровень 3** (сверловка/выемки). Значит один физический станок появляется в маршруте **дважды, на разных шагах**. Заводить либо как два рабочих центра (`CNC1-POL` ур. 2 и `CNC1-PROC` ур. 3) с общим габаритным ограничением 60×122", либо разрешить одному work_center участвовать в двух уровнях. Модель обязана это допускать — иначе маршрут детали, у которой есть и полировка контура, и вырез, построится неверно.
- **Ключевой инсайт:** максимальный размер детали — НЕ константа, а функция от МАРШРУТА через набор станков. Одна и та же деталь может проходить через печь, но не проходить фацетный станок (разные лимиты). Функция `check_route_fits()` / `checkRoute()` в JS-прототипе проверяет весь список операций разом и возвращает все нарушения.
- Печь 90×150" не берёт лист 130×96" целиком (96 > 90 по короткой стороне) — целый лист закалить нельзя, только раскроенные детали.

**`service` (услуга)** — притупление кромки, полировка, фацет, сверловка, ЧПУ.
- `stage`: pre_temper (вся механика — закалённое стекло не обрабатывается) / post_temper / any
- `affects_size` — операция съедает материал, размер реза больше финального
- `service_allowance` — припуск на рез, зависит от услуги И толщины, отдельно ширина/высота (SEAM 0, POLISH 1/16", BEVEL 1/8", CNC 1/4" — для 6мм)
- `service_work_center` — связь услуга↔станок, лимиты можно переопределить на уровне связки

## 5. Ценообразование (только что спроектировано, нужно доработать)

### 5.1 Бизнес-правила от пользователя
- Модель: **закупка по себестоимости → своя наценка → плюс услуги → плюс energy surcharge**.
- Минимальная площадь к оплате: **4 ft²** по умолчанию, но может быть **2 или 3 ft²** для отдельных случаев (переопределение на уровне материала или клиента).
- Округление размера для расчёта площади к оплате: **вверх до целого дюйма** (23.25" → 24"). Это отдельно от размера реза/себестоимости, который считается по факту с припусками.
- Валюта закупки зависит от точки поставки (см. `source` выше), не от материала напрямую.
- **Профит виден ТОЛЬКО владельцу.** Уточнено пользователем 21 авг 2026. Раньше в этом документе стояло «админ и специально допущенные» — **это исправлено: админ теперь роль техническая и прибыль по умолчанию НЕ видит.** Право видеть прибыль привязывать к конкретному пользователю-владельцу, а не к админской роли, иначе оно утечёт вместе с админскими правами. Это касается всей цепочки: цена закупки, точка поставки, фрахт, курс, себестоимость, маржа/наценка в процентах, отчёты P&L. Наценка в процентах тоже скрывается — иначе через неё вычисляется себестоимость. Скрытие должно быть на уровне ВЫДАЧИ ДАННЫХ (API/отчёт/экспорт), не только на уровне экрана — иначе Excel-экспорт или печатная форма всё равно унесёт цифры.

### 5.2 Что уже реализовано в прототипе v3
- Разделение: **фактическая площадь** (для себестоимости, с припусками на услуги + % отхода) vs **площадь к оплате** (округлённая, с учётом минимума).

### 5.4 Отпечаток Makeup вместо библиотеки конфигураций (решение от 21 авг 2026)

Глобальная библиотека конфигураций отвергнута по комбинаторике (раздел 2). Но у order-scoped Makeup есть цена этого решения, и её надо закрыть осознанно: **одинаковый пирог в двух заказах — это две разные записи с разными id**. Следствия: нельзя спросить «сколько таких стеклопакетов мы сделали за год», нельзя вести себестоимость и цену по пирогу, постоянный клиент каждый раз собирает свой стандартный пакет заново.

**Решение — не каталог, а вычисляемый ключ.** `makeupFingerprint(m)` считается из **id** (стекло, закалка, поверхность покрытия, spacer, газ, герметики — в фиксированном порядке), а не из названий, ровно как `fingerprint: shp-…` уже сделан для Shape. Хранить каталог не нужно: одинаковые makeup в разных заказах схлопываются сами, и на этом строятся отчёты и себестоимость по пирогу.

**Не горит.** В отличие от журнала событий, отпечаток вычисляется из данных, которые уже сохранены (makeup хранит именно id, а не тексты), — значит его можно посчитать задним числом по всем старым заказам. Поэтому идёт вместе с ценообразованием, Этап 6.

**Следствие для справочников:** раз Makeup ссылается на продукт по id, позицию каталога **нельзя удалять** — старый заказ покажет `?` вместо кода стекла (`salesGlassCodeForPane` подставляет `'?'`, если продукт не найден). Только пометка «неактивен». Заложено в Этап 5 плана.

## 6. Модульная структура (актуальное решение — переработать группировку)

Пользователь потребовал: **модули по бизнес-домену/владению**, не по "удобству ввода". Каждый модуль отдельный, но связан через ссылки, и у каждого должен быть СВОЙ ОТЧЁТ (что/как/сколько делалось).

| Модуль | Владеет данными | Отчёт |
|---|---|---|
| **Склад / инвентаризация** | Номенклатура, материалы, подложки, покрытия, толщины, листы; остатки, партии, обрезь, движения | Расход, оборачиваемость, что лежит мёртвым грузом |
| **Закупки** | Поставщики, точки поставки, цены закупки, заказы поставщику, приёмка, MRP | Динамика цен, поставки в срок, недопоставки |
| **Продажи** | Клиенты, прайсы, скидки, котировки, заказы, ACK | Выручка, маржа по продукту (скрыто не всем), конверсия котировок |
| **Производство** | Станки, услуги, маршруты, план, детали в работе, бой и перезаказ | Выработка, загрузка станков, брак и причины |
| **Отгрузка** | Стойки, комплектация, маршруты, накладные | Отгружено в срок, простой стоек |
| **Финансы** | Фактическая себестоимость, счета, интеграция с бухгалтерией | P&L по продукту, где теряется маржа |

**Ядро (общее для всех модулей, не отдельный модуль):**
- Единицы измерения, валюты, курсы
- Пользователи и права
- **Журнал событий** — критично: отчёты "что как сколько делалось" читаются ИЗ ИСТОРИИ СОБЫТИЙ, не из текущего состояния таблиц. Текущее состояние БД не хранит "сколько закалили в июле" — если события не писать с первого дня, задним числом это не восстановить. Каждое действие в любом модуле обязано писать событие: кто, что, когда, сколько, над каким объектом.

**Важно:** прототип v3 (файл glass_erp_v3.html) сгруппирован ПО-СТАРОМУ — вкладки "Материалы / Каталоги / Производство / Закупка / Продажа / Расчёт". Это НЕ переделано и остаётся как справочный прототип модели материалов/цены, не как основа для дальнейшей доменной структуры.

**Доменная оболочка построена и живёт в репозитории** — состав экранов и что в них реально работает см. раздел 10. Кратко: Dashboard, Users, Customers, Sales (Draft Sales Orders + Makeup Builder), Configurators (Production Shape + Adaptive Muntin), Optimization, Production. Домены Inventory / Purchasing / Shipping / Finance пока только в меню.

**Чего в оболочке ещё нет из требований этого раздела:**
- журнала событий — а без него отчёты «что как сколько делалось» построить нельзя задним числом;
- собственных отчётов у каждого домена;
- модель материалов и цены (разделы 4–5) в новую оболочку не перенесена, остаётся в справочном `glass_erp_v3.html`.

## 7. Права доступа (спроектировано словами, не реализовано)

- **Сейчас:** только админ (стадия разработки).
- **В перспективе:** разделение по модулям, для каждого — просмотр vs изменение.
- **Уровней не два, а четыре:** нет доступа / просмотр / изменение / **согласование** (например кладовщик может списать бой, но не может утвердить списание — разные права на одно действие).
- **Права нужны и на уровне полей, не только модулей.** Пример: продажник видит цену продажи, но не видит себестоимость и маржу — это одна колонка внутри ЕГО ЖЕ экрана заказа, не "доступ к модулю Финансы" целиком.
- **Профит закрыт по умолчанию** — только админ + явно допущенные пользователи (см. раздел 5.3).
- **Архитектурное решение:** одна точка проверки прав — функция вида `можно(роль/пользователь, модуль, действие)`, вызываемая при КАЖДОМ действии. Не размазывать проверки по интерфейсу — иначе разделение прав станет отдельным проектом на месяц вместо правки одной таблицы.
- **Проверка должна быть на уровне выдачи данных (API), не на уровне UI** — спрятанная кнопка/колонка не защита, данные всё равно приедут в браузер через тот же запрос.
- **Цеховые терминалы — особый случай:** учётка принадлежит станции/терминалу, а не человеку; конкретный оператор идентифицируется сканом бейджа при действии. Если заставлять логиниться/разлогиниваться на каждой смене — операторы будут работать под одной общей учёткой, и журнал событий (см. раздел 6) станет бесполезным.
- **Реальные роли названы пользователем (21 авг 2026): `Продажи` · `Бухгалтер` (внутренний, по заказам) · `Админ` · `Владелец`.** Четыре, а не семь. ~~В коде засеяно семь выдуманных ролей~~ — **приведено 21 авг 2026, Этап 3C:** `ROLES=['Продажи','Бухгалтер','Админ','Владелец']` в `src/erp/data.js`, `SAFE_DEFAULT_ROLE='Продажи'` (неизвестная роль падает в самую слабую, а не в первую попавшуюся). Названия хранятся по-русски и переводятся словарём `i18n.js` — в интерфейсе это Sales · Accounting · Admin · Owner. **Сами права ещё не реализованы: роль сегодня только название.**
- **Прибыль видит только `Владелец`** (раздел 5.1). `Админ` — техническая роль: настройки, справочники, пользователи, но не деньги.
- **Цех, отгрузка и снабжение как именованные пользователи пока не заводятся.** Пользователь их не назвал, и это согласуется с решением выше по цеховым терминалам: учётка принадлежит станции, а конкретный рабочий опознаётся сканом бейджа при действии. Если это прочтение неверно и в цеху нужны личные учётки — переспросить, не додумывать.

**Пять багов, найденных пользователем при ревью, и их причины:**
1. **`1″` отображался как `57/64″`, `10″` кромка нотча — как `10-7/64″`.** Причина: `ssStairs` анкерил лесенку нотча от вершины bounding box, а не от реального конца обрезанного пролёта, из-за чего первое ребро нотча забирало на себя наклон ребра A. Исправлено анкеровкой от `pVert` с выводом горизонтальных отрезков из фактических концов вертикальных.
2. **Скосы нотча не показывались внутри контура фигуры**, хотя прежняя (не GitHub) визуализация их рисовала. Причина — старая цепочка размеров не включала кросс-осевые рёбра нотча. Добавлена `shapeAnnChainSegments` с явным подбором рёбер по стороне.
3. **Левая мини-панель писала «невалидна», правая панель — «валиден» для той же фигуры**, и смена фигуры туда-обратно «чинила» левую. Причина — `refreshShapeEditor()` обновлял только правую колонку DOM. Исправлено точечным обновлением обеих панелей с сохранением фокуса поля ввода.
4. **Двойной скос становился невалидным сразу после ввода**, но валидным после переключения на другую фигуру и обратно — тот же класс бага, что и №3.
5. **Раздел «Corner blocks · Out of plumb / level» показывался, даже когда ни один угол не выбран.** Исправлено: секция видна только когда выбран хотя бы один угловой блок (`shapeCornerSectionsVisible`).

**Скрытая геометрия из снятых угловых блоков (отдельный, более глубокий баг).** После первого исправления пользователь показал точное воспроизведение: фигура `25″ × 92″` продолжала хранить невидимый вынос угла TL `2″`, хотя угловой блок в интерфейсе был снят. Первая правка в `ssNormalize` не сработала для уже сохранённых в localStorage фигур, потому что `ssIsModel()` делает ранний выход для «уже нормализованных» моделей и не перепроверяет их повторно. Исправление перенесено в сам `ssIsModel()`: модель без выбранных угловых блоков считается нормализованной только тогда, когда её `cornerOffsets` пусты — иначе она обязана пройти повторную нормализацию, которая обнулит осиротевшие координаты. Проверено прогоном с намеренно испорченной фигурой, засеянной прямо в `localStorage`.

**Нейтральный старт Smart-Shape.** По прямому требованию пользователя («пусть смарт шейп изначально не хранит никакую фигуру, максимум прямоугольник, но без скосов и ничего прочего») новый Smart-Shape открывается прямоугольником `1″ × 1″` без единого скоса, элбоу или углового выноса. Чтобы собрать стеклопакет с ламинированным листом, создавали **фиктивный товар, равный всему триплексу целиком**, и вставляли его в слот Lite 2. То есть это не небрежность кладовщика, а **обход отсутствующей модели**.

  **В новой оболочке этот обход уже не нужен.** Makeup поддерживает ламинированный лист штатно: `category: 'laminated'` с полями `laminated: {outerGlassProductId, interlayerProductId, innerGlassProductId}`, и общая толщина считается со слоем интерлейера — есть зелёный регрессионный тест (`6 мм + .030 PVB + 6 мм = 12.762 мм`). Причина, породившая фиктивные товары, устранена.

  **Обход не поддерживался — 9 из 12 толщин не сходятся с собственным составом:**

  | Позиция | Записано | Состав | Расчёт |
  |---|---|---|---|
  | `4MM/4MM .15 EVA` | 8.00 | 4+4 + .015″ | 8.38 |
  | `4MM/4MM .30 EVA` | 8.00 | 4+4 + .030″ | 8.76 |
  | `4mmHS/0.03EVA/4mmHS` | 8.00 | 4+4 + .030″ | 8.76 |
  | `10mm Lami .030` | 11.20 | 5+5 + .030″ | 10.46 |
  | `16mm Lami . 060` | 17.22 | 8+8 + .060″ | 17.22 ✓ |

  Первые две строки показывают механику ошибки: **два разных интерлейера дают одну и ту же записанную толщину 8.00** — то есть толщину просто набивали как сумму стекла, а интерлейер не считали вовсе. При этом две сошедшиеся строки используют разные конвенции: `12mm Lami .060` посчитана по номиналу (6+6), `16mm Lami . 060` — по факту (7.85+7.85). Единой договорённости не было. `10mm Lami .030` записана как 11.2, что соответствует интерлейеру **.060″, а не .030″** из собственного названия.

  **Решение, которое остаётся за пользователем: покупаем ламинат или делаем сами.** В данных есть оба случая. `4mmHS/0.03EVA/4mmHS` — сначала HS, потом склейка, то есть **своё производство**: на складе лежат компоненты, ламинация — шаг маршрута. `10mm Lami .030 Annealed cut to size` — «cut to size», то есть **покупной лист**, и тогда это законная позиция каталога со своей ценой и размером листа. Правило для этого различения в архитектуре уже есть — `coating.applied_by` (`primary_manufacturer` / `offline_coater` / `fabricator`) из раздела 4.2: *«если наносим сами, это генерирует шаг маршрута, а не позицию закупки»*. То же правило распространяется на ламинацию отдельным полем `laminated_by`. **Не решать за пользователя** — по каждой из 12 позиций нужен его ответ «покупаем / делаем».

  **Следствие для приёмки Ф2.** Исторические заказы в Spil ссылаются на эти фиктивные товары. Когда придут эталонные заказы для сверки цены (раздел 11, п. 9), строка вида `Lite 1 = 6CL · Cavity · Lite 2 = 3MM3MMEVALAMI` должна разворачиваться в `Lite 2 = laminated(3 мм + .015″ EVA + 3 мм)`. Нужна разовая таблица соответствия на 12 строк — иначе сверка состава деталей не сойдётся.
- **Давальческое сырьё клиента лежит в том же справочнике:** `6TEMP`, `10TEMP`, `12TEMP` = «CUSTOMERS OWN CLEAR GLASS», у всех трёх себестоимость 0 и остаток 0. Отдельная ловушка: **`TEMP` здесь означает не «tempered», а «стекло клиента»** — при переносе легко прочитать наоборот. Подробный разбор и вывод по модели — раздел 9к.

- **Разделение ЧПУ подтверждено данными.** `Polishing(2)` и `Processing(3)` — отдельные шаги в самом Spil, что совпадает со словесным ответом пользователя. Это не наша интерпретация, а его собственная модель.

**Аномалия: `WASHING = 12`.** Двенадцатый номер ставит мойку после отгрузки. Физически мойка обязана идти перед сборкой стеклопакета — грязное стекло в пакет не заклеивают. Вероятно станцию завели позже, и она получила следующий свободный номер. Настоящее место — между `Tempering(5)` и `IGU(9)`. **Уточнить у пользователя, не переставлять молча.**

**Открытый вопрос: что означает галочка `Default Station`.** Отмечены Cutting, Processing, Tempering, Lamination, IGU, Shipping Ready, Shipping. Два прочтения, дающие разные маршруты: либо «станция входит в маршрут по умолчанию» — но тогда странно, что каждая деталь ламинируется и становится стеклопакетом; либо просто «станция активна». От ответа зависит построение маршрута — не додумывать.

**Архитектурный вывод: станция ≠ станок, и в Spil есть только первый слой.** `Main Station` — это шаги маршрута. Физического оборудования с габаритами в этой таблице нет, а именно от него зависит, изготовима ли деталь: 88 × 140″ проходит печь (90×150), но не проходит фацетный станок (70×100). Целевая модель это разделяет — `work_center` с `max_width_in`/`max_length_in` и функция `check_route_fits()` (раздел 4.2), — а оболочка пока смешивает: у станции есть и уровень, и габариты. **При переносе развести на две сущности:** станция (шаг маршрута, порядок) и станок (железо, лимиты, `batch_mode`), станок ссылается на станцию. Один станок может стоять на двух станциях — ЧПУ у пользователя работает и на `Polishing`, и на `Processing`.

**`batch_mode` — новое обязательное поле станка.** Печь, автоклав и линия СП работают садками и партиями, остальное поштучно. Без этого признака планирование Ф4 построить нельзя: в печь планируется садка, а не деталь.

**Файлы под заполнение:** `PRODUCTION_STATIONS.csv` (заполнен по скриншоту, пользователь правит `always_or_optional` и смысл спорных станций) и `PRODUCTION_MACHINES.csv` (слой станков, заполняет пользователь).

### 9з. Саб-станции Spil: три слоя вместо двух (21 авг 2026)

> **Поправка 22 авг 2026.** Механизм перезаписи шагов ниже объяснён коллизией кодов в справочнике. Это симптом, а не причина. Настоящая причина — «станция» в Spil является экраном сканирования, а подстанция — разрезом отчёта. См. раздел 9м; читать его до того, как переносить структуру Spil.

Вторая выгрузка пользователя — таблица саб-станций, **34 строки**. Вместе с `Main Station` из раздела 9ж выясняется, что модель цеха в Spil трёхслойная, и это правильная модель, которую надо перенести:

| Слой | Что это | Сколько | Соответствие целевой модели |
|---|---|---:|---|
| **Main Station** | шаг маршрута | 12 | последовательность уровней |
| **Sub Station** | физическое место работы | 33 (+ заглушка `Not to Use`) | `work_center` из раздела 4.2 |
| **Default Service** | что попадает в счёт | 19 | `service` из раздела 4.2 |

Разделение содержательное: три станка `CNC 1/2/3` выставляются одной услугой `CNC 1` — клиенту всё равно, на каком резали, а цеху это три разных места с разной очередью и габаритами. **Оболочка сейчас смешивает всё в одну сущность `station`; при переносе развести на три.**

**Подтверждено наблюдение пользователя «CNC процессинг вместе с CNC обработкой».** На станции `Processing` девять саб-станций: `Drilling 1/2/3`, `CNC 1/2/3`, `Cut-out CNC 1/2`, `Vertical CNC`. Сверловка и ЧПУ-обработка в одной куче, хотя это операции с разными припусками. Аналогично на `Polishing`: четыре саб-станции `Polishing 1/2/3/4` биллятся одной услугой `Polishing 2`, при этом у `Polishing 3` и `Polishing 4` код `MITR` — то есть это митра, а не полировка. Название, код и услуга говорят три разные вещи.

**Механизм «иногда оно переписывает некие шаги» найден: четыре кода носят по нескольку саб-станций.**

| Код | Кто делит | Последствие |
|---|---|---|
| `ARIS` | Machine Arrising · Manual Arrising | **разные услуги** (`Machine Arrising` и `Arrising`) — по коду не восстановить, что выставлять в счёт |
| `COCNC` | Cut-out CNC 1 · Cut-out CNC 2 | два станка полностью неразличимы |
| `MITR` | Polishing 3 · Polishing 4 | разные категории Spil (17 и 35) под одним кодом |
| `PANT` | Spray · Roller · Booth | три способа покраски одним кодом |

Дороже всего `ARIS` — машинное и ручное притупление это разная работа с разной ценой. **Вывод для нашей модели: код рабочего центра обязан быть уникальным, проверка на дубль — на уровне справочника, а не на совести оператора.**

### 9к. Давальческое стекло клиента — недостающая ось модели (21 авг 2026)

Пользователь объяснил происхождение `6TEMP` (21 авг 2026). Позицию кто-то завёл под два разных сценария:

1. **Закалка чужого материала** — клиент привозит своё стекло, мы только закаливаем.
2. **Стеклопакет с листом клиента** — например `6mm Clear + 6TEMP`, где второй лист предоставил клиент.

Реальную толщину при этом **пишут словами в описание строки**: «3/4/5/6/8 mm customer own glass». То есть один код с `Thickness = 5.85` покрывает пять разных физических толщин.

**Это не кривое название, а отсутствующая ось: чей материал.** Ровно та же логика, что в разделе 4.1, где закалка вынесена из материала отдельной осью, потому что «закалённого стекла на складе не бывает». Здесь так же: **стекло клиента — это не отдельный товар, это тот же материал с другим владельцем.** Владение принадлежит строке заказа и компоненту, а не позиции каталога.

**Чем это опасно сейчас — считаемо.** Система берёт толщину из карточки, то есть 5.85 мм, независимо от того, что реально привёз клиент. Стеклопакет `6 мм Clear + спейсер 1/2″ + 6TEMP`:

| | расчёт системы | если клиент привёз 4 мм |
|---|---|---|
| Общая толщина | 5.85 + 12.7 + 5.85 = **24.4 мм** | 5.85 + 12.7 + 4.0 = **22.55 мм** |

Расхождение **1.85 мм** — это подбор спейсера, посадка в раму и герметизация. Ошибка не в отчёте, а в изделии.

**Решение пользователя (21 авг 2026): завести `COG` — Customer Own Glass — отдельной позицией на каждую толщину**, а цену править в конфигураторе. Принято, с двумя уточнениями.

Предложение снимает главный риск: у `COG-4` толщина 4 мм, у `COG-6` — 6 мм, поэтому расчёт толщины пакета становится верным. Именно это ломалось, когда одна карточка `5.85` покрывала пять толщин.

- **Позиции:** `COG-3 · COG-4 · COG-5 · COG-6 · COG-8 · COG-10 · COG-12 · COG-15 · COG-19` — по толщинам, реально встречающимся в каталоге.
- **Уточнение 1: цена и себестоимость = 0 в самой карточке, а не правкой в конфигураторе.** Ручное исправление цены работает ровно до первого раза, когда о нём забудут, — и клиент получит счёт за стекло, которое привёз сам. Ноль по умолчанию делает забывчивость безопасной; в счёт идут только услуги. Если конкретная работа требует другой цифры — тогда правка руками, но как исключение, а не как норма.
- **Уточнение 2: признак `supplied_by: own | customer` полем, а не только префиксом кода.** Стоит ничего, но делает надёжными две вещи: отчёт «сколько чужого стекла обработали» и логику боя (см. ниже). Иначе всё держится на том, что код начинается с `COG`.
- Склад: чужой материал не наш остаток, но обязан быть **прослеживаемым по заказу** — мы физически храним чужую собственность.
- Для сценария «только закалка» строка заказа вообще не содержит материала — там лишь услуга над материалом клиента.

**Тонированное и с покрытием бывает — подтверждено пользователем 21 авг 2026.** Решается **не каталогом, а гейтом при приёме материала.** Заводить `COG-{толщина}-{тип}` нельзя: 9 толщин × 4 типа = 36 позиций, то есть возврат к комбинаторике, из-за которой отвергнута Configuration Library (раздел 2).

- Девять позиций `COG` остаются девятью. У всех **`temper_mode = unknown`** — честное «не знаем», а не «отожжённое».
- Подложка, покрытие и закаливаемость заполняются **на строке заказа при приёме**: `cog_substrate`, `cog_coating`, `cog_temperable` (`yes`/`no`/`unknown`), `cog_confirmed_by`.
- **Жёсткое правило: `unknown` + закалка в маршруте = блокировка.** Пока никто не ответил, деталь в печь не уходит.

**Почему это гейт, а не необязательное поле.** Мягкое покрытие бывает закаливаемым и незакаливаемым — у пользователя это различие уже закодировано как `Q` против `E` (раздел 9е). Незакаливаемое soft-coat в печи мутнеет, стекло в брак. **Но стекло чужое:** это не перезаказ со склада, а уничтоженная собственность клиента. Поле `cog_confirmed_by` фиксирует, кто подтвердил закаливаемость — если подтвердил клиент и стекло помутнело, это его риск; если не спросил никто, риск фабрики. Реализация — Этап 5.

**Следствие для Этапа 7 (разузлование и маршруты), которое легко упустить.** Компонент из давальческого стекла должен нести этот признак: **бой чужого стекла — это не перезаказ со склада, а звонок клиенту.** Логика remake принципиально другая, и если признака нет на компоненте, цех узнает об этом только когда полезет за заменой в стеллаж.

**Мелочь, показывающая, что справочник никто не сопровождал:** из трёх позиций `10TEMP` и `12TEMP` лежат в группе `CUSTOMERS CLEAR GLAS`, а `6TEMP` — просто в `GLASS`. Даже группировка трёх строк не выдержана.

### 9л. Ответы пользователя по цеху — реальный маршрут (21 авг 2026)

Десять уточнений по разделам 9ж–9и. Часть меняет модель маршрута, а не только справочники.

**1. Мойки в маршруте нет вообще — это база.** Уточнено пользователем в тот же день, и это **упрощает** модель, а не усложняет. Дословно: *«станции мойки не нужно показывать в пути производства, потому что это БАЗА. Стекло не запустят в закалку если грязное, IGU не соберут если стекло грязное»*.

Физически моек **две**: одна у печи закалки, вторая **прямо на станции сборки СП** — стёкла моются парами, тут же ставится распорка и собирается пакет.

> **Вывод: мойка — не шаг маршрута, а неотъемлемая часть операций «закалка» и «сборка СП».** Станция `WASH` удалена из списка станций (осталось 11), обе мойки заведены **станками при своих станциях**: `WASH-T` при `TEMP`, `WASH-IGU` при `IGU`.
> **Но габарит мойки всё равно нужен** — он ограничивает максимальный размер детали не хуже печи, просто не как отдельный шаг, а как лимит станции.

**Требование «станция может входить в маршрут несколько раз» при этом остаётся**, только обосновано оно не мойкой, а ламинатом: в маршруте `резка → аррис → закалка → ламинация → polish lami` станция `Polishing` встречается **дважды** — сначала притупление, потом полировка ламината. Значит `routing_step` (раздел 8) обязан быть **упорядоченным списком шагов со своим номером внутри детали**, а не ссылкой на станцию с её глобальным `seq`.

**Три вещи, которые сломаются при прямом переносе:**

1. **`<marker id="a">` — коллизия идентификаторов.** Это ровно тот баг, который уже ловили в разделе 9в: `url(#…)` в SVG резолвится в **первый совпавший id документа**, и печатная копия «одалживала» маркер у скрытого превью. Там это чинилось `printSheetUniqueIds`. Здесь id ещё и односимвольный — в общей странице ERP рядом с чертежами Shape и Muntin он гарантированно столкнётся. **Отступы и опорный угол — параметры заказа, а не константы** (уточнено пользователем 21 авг 2026). Единственно верного значения нет: обычно ставят минимум `1″`, но допускается и `0`. Отсюда два правила для переноса:

- **Не валидировать минимум.** `0` — законное значение, проверка «отступ ≥ 1″» была бы выдумкой.
- **`1″` — предзаполненное значение, а не правило.** В исходном файле стоит `1 1/4″`; берём `1″` как более частое, но это просто стартовое значение поля.
- **При отступе `0` размерная линия вырождается:** в коде она рисуется от первой точки до кромки, а на нуле это отрезок нулевой длины с двумя стрелками друг на друге. Не ошибка расчёта, но на чертеже выглядит грязно — при нулевом отступе размер просто не выводить.

Валидации в модуле нет вообще: индексная арифметика размерных линий предполагает минимум по две колонки и два ряда точек. При переносе накрыть тем же правилом «невалидное не сохраняется и не экспортируется», что и Shape.

**Цифровая керамическая печать — аутсорс поневоле.** Машина есть, но **не работает около года** (нет деталей). Услуга остаётся в прайсе: когда нужна, стекло отдают на сторону и перевыставляют клиенту. Это вводит в модель понятие, которого не было: **`service.performed_by` = `in_house` | `outsourced` | `either`**, аналогично `coating.applied_by` из раздела 4.2. Для Ф4 существенно: у такой операции маршрут уходит за пределы цеха и возвращается, со своим сроком и транспортом. Станок заведён как `DIGI` со статусом «не работает».

**4. Painting = опаци-коат, подтверждено.** Спрей / ролик / камера выбираются **по размеру детали**. Значит это **одна услуга и три станка**, а метод — решение цеха, а не продажи. В конфигураторе метод не спрашивать.

**5. `PPLAM` внутри `IGU` — ошибка настройки Spil.** Должна называться `IGU` или `Assembly`. Переименовано.

**6. Три станции получили точные места в маршруте:**
- **Heat Soak** — отдельная машина **после закалки**, по запросу клиента. Услуги в прайсе есть (`4/5/6/8/10/12 HTSK`), просто не были привязаны.
- **Sandblasting** — после закалки; **а если деталь не закаляется — после обработки кромки**. Позиция зависит от того, есть ли в маршруте печь. Ещё один условный шаг.
- **Polish Laminate / CNC Lami Polish** — одни из последних операций: кромку ламината обрабатывают **после склейки, а не до**.

**Маршрут ламината со слов пользователя:** `резка → кромка (аррисинг — для безопасного перемещения стекла по цеху) → закалка → ламинация → polish lami / shape polish lami`.

> Отсюда важное для `service.stage` (раздел 4.2): полировка ламината — **`post_temper`**, в отличие от обычной полировки, которая `pre_temper`. Правило «вся механика до печи» имеет исключение, и оно именно здесь. Также объясняется, почему `RA` ROUGH ARRIS — дешёвая отдельная услуга: это не финишная кромка, а притупление для безопасного хождения стекла по цеху.

**7. `CN 1001` — никогда не использовалась, удалить.** Помечена в `PRODUCTION_SERVICES.csv`.

**8. Цены по диапазонам сворачиваются.** Подтверждено: **одна услуга, цена зависит от толщины.** Значит фацет (4 позиции), heat soak (6 позиций) и отверстия (5 позиций по диаметру) становятся тремя услугами с таблицей цен, а не пятнадцатью товарами.

**9. `TEMP` — коллизия снимается сама.** Раз для стеклопакетов появился `COG`, старые `6TEMP`/`10TEMP`/`12TEMP` уходят; закалка чужого стекла — это **просто услуга закалки** над материалом `COG`, без отдельного товара.

### 9м. Как цех работает на самом деле — терминалы, подстанции, L-номера (22 авг 2026)

Разбор с пользователем 22 августа. Меняет не справочники, а понимание того, что означают данные Spil. **Раздел 9з объяснял перезапись шагов коллизией кодов — это было неверно; настоящая причина ниже.**

**1. «Станция» в Spil — это экран, а не шаг маршрута.** Дословно: *«сотрудники имеют компьютер на производстве, к которому привязана станция CNC, у них есть экран, где они сканируют то, что они сделали… для cnc processing у них тот же экран и та же станция CNC + shape polish + cnc lami polish… экраны под станции они не умеют переключать или не хотят»*.

Скан говорит «на CNC сделано», но не говорит **какая операция** — поэтому следующая запись ложится на то же место и затирает предыдущую. Самый дорогой случай, названный пользователем: **`CNC` показывает, что петли уже выполнены, хотя их не делали.** Это не потеря истории, а ложное утверждение о выполненной работе: деталь уезжает без петель, а закалённое стекло не досверливается.

> **Вывод: терминал — отдельная сущность, чистое устройство ввода. Ключом шага маршрута он не бывает никогда.**

**2. Подстанция в Spil — это разрез отчёта, а не единица цеха.** Дословно: *«Спил не может дать нам отчёт отдельно по пользователям, которые выполнили ту или иную операцию, и поэтому они разбили на станции, чтобы показывать отчёт cutting1 cutting2… хотя достаточно одной станции Cutting и два стола и два юзера»*.

`cutting1` / `cutting2` — это **люди**, а не столы. Любое измерение, которого не хватало отчётам, заводилось строкой подстанции. Поэтому в 33 подстанциях лежит вперемешку минимум четыре разные вещи: люди, станки, операции и обработки.

> **Подстанции не переносятся.** Все разрезы (человек, станок, операция, смена) — группировки журнала событий. Это второй, практический аргумент за Этап 4: без журнала справочник цеха начинает пухнуть выдуманными строками, ровно как у Spil.

**Что схлопывать нельзя** — выглядит дублями, но ими не является: `Machine Arrising` vs `Manual Arrising` (разная себестоимость, а в счёте одна позиция `RA` — маржа невидима); `Polishing 3/4` с кодом `MITR` (митра, другая операция); `Spray` / `Roller` / `Booth`; `Heat Strengthening` / `Tempering` / `Heat Soak` (это не станки, а три `treatment`); `Vertical CNC` (иной габарит).

**3. Оператор в справочнике — это допуск, а не назначение.** Пользователь прислал свою структуру с колонками `operator` и `helper` на каждой подстанции: сегодняшняя расстановка записана как структура цеха («`POLISH1` — это erik»). Завтра встанет huan, и придётся править справочник оборудования, хотя в цеху ничего не изменилось. Тот же дефект, что и подстанции, этажом ниже.

> В справочнике остаётся `default_operator` — префилл экрана. Правда о том, кто сделал, приходит со скана и живёт в событии. `helper` — новый факт: на части мест работают вдвоём, значит событие несёт исполнителя **и** напарника.

**4. Одно рабочее место навещается несколько раз, и разница не в железе, а в моменте.** Дословно про ламинат: *«ламинирование и отверстия мы делаем на CNC, чтобы добиться идеального соответствия… after tempering / hs потом ламинирование и после ламинирования процесс cnc lami shape polish»*.

Маршрут ламинированной детали: два листа **параллельно** проходят резку, притупление, отверстия на ЧПУ и закалку; сходятся на ламинации; после склейки — полировка ламината **на том же ЧПУ**. `CNC1` встречается **трижды**: дважды до печи и один раз после. Если ключом шага сделать станцию или станок, третий визит затрёт первый.

Следствия:
- **`stage` (`pre_temper` / `post_temper`) — свойство операции, а не станции.** Отверстия обязаны быть до печи, полировка ламината обязана быть после — при одном и том же железе.
- `routing_step` — упорядоченный список со своим номером внутри детали (уже записано в 9л, здесь получает второе, более сильное обоснование).
- **Маршрут не линия, а дерево:** компоненты идут параллельно и сходятся на ламинации и на сборке СП. Моно-стекло не сходится ни с чем.

**5. L-номер — идентичность компонента, которой в модели не было.** Дословно: *«каждое стекло это отдельный объект, у которого есть стикер, стикер это некий l-number (928481471), который идёт по порядку и создаётся автоматически… каждое стекло обрабатывается по отдельности»*.

- **Выдаётся при сохранении заказа в производство.** С этого момента стекло — объект, ожидающий резку. Счётчик по образцу `nextSalesOrderNumber` (`sales/data.js:147`).
- **Каждое стекло — отдельный объект.** Ламинированная панель makeup (`category === 'laminated'`, поля `outerGlassProductId` / `innerGlassProductId`) даёт **два** L-номера, не один.
- Правило разворачивания: **листы makeup × количество строки; ламинированный лист даёт два стекла вместо одного.**
- **Сверлят по отдельности, не в стопке.** Совпадение отверстий гарантировано не аккуратностью оператора, а моделью: все стёкла строки ссылаются на **один и тот же Shape** — у строки один `shapeRef` с одной ревизией и одним отпечатком. Различаются только толщина и материал, и они приходят из Makeup.
- **Слияние не создаёт нового объекта.** На стекло клеятся оба стикера, оба L-номера живут дальше. «Юнит» — понятие системы, а не отдельная железка со своим номером.
- **Финальный стикер** печатается по запросу клиента и описывает состав изделия (пример пользователя: `IGU 6cl + 6sb60`). **Макет стикеров пользователь пришлёт отдельно — до этого поля финального стикера не проектировать.**
- **Скан после склейки:** сканируется любой из стикеров; система знает, что они склеены в одно изделие, и закрывает шаг на блоке. «Главного» стикера нет.
- **Выданный L-номер не переиспользуется никогда.** Стикер может быть уже напечатан и наклеен, когда клиент меняет заказ. Уменьшили количество — лишний компонент отменяется, а не отдаётся другому стеклу. Это же лучший аргумент за статус `confirmed` из Этапа 8: после подтверждения состав замораживается.

**6. Как экран ведёт себя при скане.** Один экран, переключать ничего не нужно — это **условие задачи, а не то, что надо чинить**. Оператор сканирует стикер → терминал показывает открытые операции этой детали для этого рабочего места, все отмечены заранее → он подтверждает одним нажатием либо снимает галочку с того, чего не делал.

Подтверждено пользователем: **на ЧПУ один человек берёт стекло и доводит его до конца**, между станками деталь не бегает. Значит несколько операций одного места закрываются одним сканом, и это корректно, а не упрощение.

> **Главный выигрыш: закрыть операцию, которой нет в маршруте детали, физически невозможно** — на экране её просто нет. Случай «`CNC` показал петли выполненными» не может возникнуть в принципе.

**7. Итоговая модель цеха.**

| Что | Чем является | Ключевое свойство |
|---|---|---|
| Станция | шаг маршрута, 11 штук | порядок, `always` / `optional` |
| Операция | что именно делают | цена, скорость, единица, `stage` до/после печи |
| Рабочее место | где делают | габарит, `batch_mode`, список операций; может служить двум станциям |
| Терминал | экран сканирования | только ввод, ключом маршрута не бывает |
| Человек | допуски к местам | в структуре цеха не живёт — живёт в событии |
| Компонент | стекло, L-номер, стикер | создаётся при сохранении заказа, сразу ждёт резку |
| Изделие | экземпляр makeup строки | не сканируется; финальный стикер по запросу |
| Маршрут | список операций компонента | дерево: сходится на ламинации и на сборке СП |
| Событие | кто · напарник · где · когда · что · над каким L | из него все отчёты без исключения |

**Сквозной проход:** заказ сохранён → выданы L-номера, каждое стекло ждёт резку → оператор сканирует стикер на своём единственном экране → терминал показывает открытые операции этой детали для этого места → отмечает сделанное → пишутся события → отчёты собираются группировкой, а не структурой. Ни одной подстанции; ни одного закрепления человека за станком в справочнике; ни одного шага, который можно закрыть, не сделав.

**8. Что осталось открытым.**
- **Габариты рабочих мест.** Есть только печь 90 × 150″, ЧПУ 60 × 122″, фацет 70 × 100″. Без них не работает `check_route_fits()`.
- **Одинаковы ли три ЧПУ по рабочему полю.** Если нет — маршрут обязан знать, на какой можно.
- **Скорости по парам операция ↔ рабочее место.** Нужны для загрузки; ложатся в `service_work_center` (раздел 4.2). Скорость принадлежит паре, а не станку: на одном ЧПУ машинное притупление и полировка контура идут с разной скоростью.
- **Смены.** В модели их нет совсем, а без них загрузку не от чего считать. Поле в настройках, не сущность.
- **Непроверенное чтение прайса (гипотеза, не факт):** `POLISH1/2/3` = полировка прямой кромки, фигурная — на ЧПУ (`shape_polish`); в ламинате та же пара `LAMPOL` против `CNC LAMI POLISH`. Пользователь это ещё **не подтвердил**.
- **Макет стикеров** — одиночного и финального. Пользователь пришлёт в рабочий день.

**9. Следствие для порядка этапов.** Компонент с L-номером понадобился **раньше**, чем стоит в плане: без него нечего сканировать, а журналу событий не о чем писать. Порядок `5 → 4 → 7` в текущем виде не работает и требует пересборки — предложение готовится отдельно.

**Файлы под заполнение, пересобранные 22 августа:** `STATIONS.csv` (11 станций, колонка `always_or_optional` заполнена пользователем) и `WORK_POSITIONS.csv` (рабочие места с колонками `operations`, `default_operator`, `default_helper`, габаритами и `batch_mode`). Заменяют прежние `PRODUCTION_STATIONS.csv` / `PRODUCTION_MACHINES.csv`: подстанций в них нет ни одной.

### 9н. Порция 1 и решения второй половины 22 августа

Продолжение 9м. Там закрыта модель цеха, здесь — её имена, связка с чертежом и первый залитый код.

**1. Правило именования станций.** Сформулировано пользователем: *«если всё будет что касается кромки — edgework, просто на стикере уже будет виден сервис arris / polish / cnc shape polish; heat treatment: tempering / heat strengthened»*.

> **Станция называется по ТИПУ РАБОТЫ. Конкретная операция живёт услугой и печатается на стикере.**

Правило шире одного примера и вычистило три названия:

| Было | Стало | Почему |
|---|---|---|
| `POLISH` | **`EDGE` · Edge work** | на станции три операции: притупление, полировка, митра |
| `Tempering` | **`HEAT` · Heat treatment** | три обработки: tempering, heat strengthening, heat soak |
| `CNC` | **`FAB` · Fabrication** | `CNC` — это железо, а не тип работы; выбрано пользователем из трёх вариантов |

`EDGE` — работа по периметру, `FAB` — работа по телу стекла (отверстия, вырезы, ноч, посадочные места под петли и клемы). Пара покрывает всю механику.

**Коды безопаснее прежних:** `HEAT` вместо `TEMP` окончательно уводит от тройной коллизии, где `TEMP` означал шаблон в услугах, стекло клиента на складе (`6TEMP`) и печь в подстанциях.

**2. Что печатается на стикере.** Маршрут детали, сгруппированный по станциям, **с количествами**:

```
L-928481471                    SO-76002 · line 1
48 × 36 · shaped               6mm Clear · lami outer

EDGE     arris · polish
FAB      2 hole · 2 hng · 3 clamp
HEAT     tempering
LAM      with L-928481472
```

Количества никто не вводит руками — они считаются из чертежа. **Термообработка печатается не как выполненная операция, а как состояние стекла:** строка `HEAT tempering` говорит следующей станции, что резать и сверлить деталь уже нельзя. Макет одиночного и финального стикера ждём от пользователя.

**3. Услуги выводятся из чертежа, и это УЖЕ НАПИСАНО.** Ключевая находка дня. `shapeDerivedRequirements` в `src/modules/shape/features.js` из готового чертежа выдаёт список работ; тест «маршрут выводится из геометрии» зелёный.

| Из чего | Операция | stationClass |
|---|---|---|
| обработка кромок | `Rough Arris` · `Flat Polish` · `Mitering` · `Beveling` | ARRISING · POLISHING · MITERING · BEVELING |
| отверстие ⌀ 3/8″–1½″ | `Drill Hole` | DRILLING |
| отверстие вне диапазона | `Machine Hole` | CNC |
| вырез | `Machine Cutout` | CNC |
| фурнитура | `Hardware Preparation` | CNC |
| радиус угла | `Radius / Fillet Machining` | CNC |

Рёбра группируются по операции: четыре кромки под одну полировку дают одну строку, а не четыре.

**Чего из чертежа НЕ выводится и не должно:** закалка, HS, heat soak, фрит, спандрель, ламинация, сборка стеклопакета — это Makeup, свойства листа и состава, а не формы. **Полный список работ по компоненту = требования из чертежа + обработки из Makeup.**

**Не хватает трёх связок, а не новой логики:**

1. строка заказа не хранит требования — `shapeRef` несёт только `{id, revision, fingerprint}`;
2. `stationClass` — словарь Shape, нужна таблица соответствия: ARRISING/POLISHING/MITERING/BEVELING → `EDGE`, DRILLING/CNC → `FAB`;
3. операции не связаны с прайсом — туда же ложатся диапазоны цены по диаметру отверстия (`1/2"-1"`, `1 1/16"-2"` и далее, раздел 9и).

> **Следствие, принять сразу: правка чертежа меняет цену.** У Shape уже есть ревизии и отпечаток, строка хранит номер ревизии. Значит подтверждённый заказ ЗАМОРАЖИВАЕТ ревизию чертежа; менять форму после подтверждения — только новой ревизией с пересчётом.

**4. Справочник фурнитуры — решено дорабатывать.** Сегодня у `hardware` поле `name` — свободный текст, а размеры выреза (`prepWidth`, `prepHeight`, `holeDia`) набиваются руками на каждый экземпляр. Две петли в двух заказах получат разные вырезы, и ни одна не связана с ценой.

> **Правило: тип задаёт форму, заказ задаёт место.** Справочник владеет геометрией выреза, отступом, минимальным расстоянием до кромки и допустимыми толщинами стекла. Заказ владеет тем, на какой кромке и на каком расстоянии.

Выбранная один раз фурнитура расходится **в пять мест**: геометрия на производственном чертеже, счёт по типам на стикере, строка в счёте по коду (`HNGS`, `CLMP` уже есть в прайсе), включение станции `FAB` в маршрут и проверка «не встанет на 6 мм, не встанет близко к кромке» ещё на этапе продажи.

**Ограничение переноса:** `shapeHardwarePolygon` строит ОДИН прямоугольник. Патч-фитинг — это вырез плюс отверстия, петля может быть парой отверстий на фиксированном шаге. В справочнике prep должен быть **набором элементов** — это расширение модуля Shape, а не только новая таблица. Заводить справочник под прямоугольники нельзя: переделывать придётся вместе с уже введёнными данными.

**5. Экран рабочего места — не только ввод.** Поправка пользователя к формулировке «терминал ничего не решает, только вводит»: экран обязан показывать очередь. Терминал **читает и пишет, но ничего не определяет** — ключом шага маршрута он не бывает.

Очередь делится надвое, и это важнее сортировки: **готово к работе** (предыдущий шаг закрыт, стекло физически здесь) и **на подходе** (деталь выше по маршруту, видно где именно). Без разделения список врёт — половина строк в нём это работа, которую сегодня физически не сделать.

Норма времени считается сама: периметр из чертежа, скорость из пары «операция + рабочее место» (`service_work_center`, раздел 4.2). Оператор видит, помещается ли очередь в смену, ещё до того как начал.

> **У садочного места экран другой.** Печь, автоклав и линия СП показывают не список деталей, а что можно поставить в загрузку вместе — одна толщина, одна обработка, помещается ли по полю. Список деталей там бесполезен: планируется садка, а не стекло.

**6. Порция 1 — залито в `main` 22 августа**, прогон «Сборка и тесты» #54 зелёный, `dist` пересобран роботом (`dc103e0`) и совпадает с пересборкой из `src` байт в байт.

Файлы: `erp/data.js`, `erp/storage.js`, `erp/i18n.js`, `views/production.js`, `views/dashboard.js`, `test/run.js`.

- **Механизм пересева справочников.** У данных появилось поле `refVersion`. Отстала версия — справочные таблицы (`level`, `station`, `glassProduct`, `heatTreatment`, `spacerVariant`, `gasProduct`, `sealantProduct`, `interlayerProduct`, `fritProduct`, `spandrelProduct`) заменяются заводскими; рабочие данные — пользователи, клиенты, заказы, чертежи — не трогаются. **Без этого правка сида в коде до работающего браузера не доезжала никогда.**
- **Этапы маршрута — все одиннадцать.** Было четыре, из них один назывался «—». Мойки среди этапов нет: она часть операций термообработки и сборки СП.
- **Один станок на нескольких этапах.** Поле `level` стало массивом `levels`. Иначе ответ пользователя «ЧПУ полирует контур и обрабатывает тело стекла» не выражался одним числом. `CNC1` стоит на этапах 2 и 3, `FURN1` — на 5. Старое `level` из сохранённых данных мигрирует автоматически.
- Из кода ушли записки «уточни у себя» — система больше не спрашивает то, на что пользователь уже ответил.

> **БАГ, КОТОРЫЙ ЧУТЬ НЕ УЕХАЛ, И ПОЧЕМУ В `DEFAULT` СТОИТ НОЛЬ.** Первая версия ставила `DEFAULT.refVersion = REFERENCE_VERSION`. Но `mergeState` копирует только те ключи, которые ЕСТЬ в сохранённых данных: у старого браузера `refVersion` нет вовсе, значение из `DEFAULT` остаётся нетронутым, система видит «версия актуальная» и **пересев не запускается никогда — ровно там, где он и нужен.** Тесты на пересев при этом были зелёными: они выставляли версию руками, то есть проверяли механизм, а не путь в него. Поймал это СТАРЫЙ тест `level строкой приводится к числу`: он засеивал станцию и ждал, что она переживёт загрузку — она пережила, а не должна была. **Правило на будущее: тест механизма не заменяет тест пути, которым в этот механизм попадают.**

**Как проверялось без node.** На машине сессии не было node, playwright-набор прогнать было нечем. **Про модули Shape и Muntin**

- Перенесены из Glass Configurator v4.5, **не переписываются с нуля**. Не «улучшать» геометрию попутно без отдельного тестового шага.

- Модуль не знает про цены, клиентов и заказы. Эта развязка сделана специально.
- Слово «модуль» = обычный файл с кодом, **не** формат Claude Skills. Не путать.
- **Чертёж (`drawing.js`) обновлён 17 авг 2026** — прямоугольные и Shape-детали используют разные, но согласованные схемы простановки размеров, см. раздел 9а перед тем как трогать этот файл снова.

Инвариант «нет углового блока — нет `cornerOffsets`» защищён в `ssIsModel()`, не убирать эту проверку без замены.

**Про интерфейс**

- Shape и Muntinbar показывать отдельными иконками-карточками, не текстовым списком. Навыки сотрудников — тоже иконками, где это помогает читать.
- **RU/EN переводит интерфейс, а не данные.** Значения из базы выводить через `raw()`; `esc()` для пользовательских значений больше не использовать, иначе переводчик снова начнёт менять содержимое базы.
- **Мобильная оболочка адаптирована 18 авг 2026** и имеет regression test на 390 px. При новых широких таблицах/редакторах сохранять локальный scroll и добавлять мобильную проверку; SVG-геометрию ради CSS не менять.
