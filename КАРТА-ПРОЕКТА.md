# Карта проекта GLASS ERP

Здесь написано **что где лежит и куда писать правки**. Сам по себе этот файл
ничего не описывает по существу — он только указывает на нужный документ.

Раньше на этом месте лежала вторая копия хендофа. Она разошлась с основной и
по номеру версии стала выглядеть свежее — из-за чего в неё писали правки,
которых потом никто не находил. Копии больше нет, вместо неё карта.

Управляющий документ проекта — **`docs/GLASS_ERP_HANDOFF.md`**, и он
**единственный**.

- Вторых копий не заводить. Ни в корне, ни под другим именем, ни «временно».
  Два документа с разной нумерацией уже дважды приводили к потере правок:
  сначала с планом (21 августа), потом с самим хендофом (1 сентября).

- **Версию поднимать всегда.** Номер — единственное, по чему видно, какой

### Последнее обновление · 11 сентября 2026 — один механизм пересборки справочников

«Дешёвая половина» слияния таблиц: четыре похожих куска пересборки сведены в
`mdRebuildTable` (`src/erp/masterdata/glass.js`). Таблицы остались отдельными
массивами — `localStorage` и формат Export/Import JSON не тронуты. Различия
(долив заводских строк, снятие легаси, миграция, дедуп) стали параметрами в
одном списке вместо россыпи `if (k==='...')`: именно их расхождение раньше
стоило багов — Opaci Coat и Backpainting не доезжали до владельца. Совпадение
поведения «до/после» доказано прогоном на шести сценариях, побайтно.
Проверено **517/517**, дважды; детали — в шапке хендоффа v5.13.

### Предыдущее обновление · 11 сентября 2026 — русский интерфейс удалён

Словарь `src/erp/i18n.js` (871 пара RU→EN) удалён вместе с `LANG`, `tx()`,
`applyLang()` и обёртками alert/confirm: русский в интерфейсе стал физически
невозможен, а не просто вычищен. Комментарии в коде остались русскими —
это документация решений. Двуязычные таблицы данных (имена станций, единицы,
термины каталога) остались двухколоночными, читается `nameEn || name`. Роли и
навыки перенесены миграцией: это хранимые значения, а не подписи. Пять узких
проверок языка заменены одной сильной.
Проверено **515/515**, дважды; детали — в шапке хендоффа v5.12.

### Предыдущее обновление · 11 сентября 2026 — этап 2: материал одной формой

Общая шапка раздела 3.1 (`materialHeader`, `src/erp/masterdata/glass.js`)
легла на все девять справочников материалов: категория, подкатегория,
закупка, заготовка под инвентаризацию. Доступ стал один —
`materialEntries(category)` / `materialById(id)` возвращают пары
`{table,row}`, не требуя знать таблицу. Экран Master Data перестроен:
пять вкладок вместо восьми (Materials · Works · Hardware · Weight norms ·
Обзор базы), девять справочников стали категориями с подкатегориями внутри.
Физическое слияние девяти таблиц в один массив НЕ сделано осознанно: после
общей формы и общего доступа оно добавляет только опрятность хранилища, а
стоит «дня переезда» живой localStorage и совместимости Export/Import JSON.
Проверено **519/519**, дважды; детали — в шапке хендоффа v5.11.

### Предыдущее обновление · 11 сентября 2026 — интерфейс стоковых позиций

Живая правка по скриншотам поверх предыдущего раздела (тот же сценарий:
клиент забрал стекло, вспомнил про стоковую дверь). GLASS / IGU MAKEUPS
больше не сворачивается сам по числу строк — открыт по умолчанию, прячет его
явная кнопка `×` (`soGlassOpen`, `src/erp/sales/orders.js`;
`salesGlassSectionClose`/`salesGlassSectionOpen`, `src/erp/views/sales.js`);
если в заказе были строки, закрытие спрашивает подтверждение. Стоковый айтем
выбирается в окне (`salesStockPickerModal()`), а не в инлайн `<select>` — с
пилюлями-фильтром по подкатегории и полем Qty у каждой строки, количество
задаётся сразу при добавлении. Подкатегория стока (`door/kit/consumable`)
стала свободным текстом с подсказкой, как семейство цвета спандрела —
владелец заводит свои подкатегории сам.
Проверено **507/507**, дважды — по модулям и по собранному `dist`; детали — в
шапке хендоффа v5.10.

### Предыдущее обновление · 11 сентября 2026 — работа = станция + цена, сток своей строкой

Полная схема мастер-данных согласована с владельцем —
`docs/MASTER_DATA_SCHEMA_2026-09-10.md`, там же список отложенного и почему.
Станция FAB упразднена: `DB.operation` и `DB.workPosition` удалены вместе с
экранами, работа (`DB.serviceRate`) несёт станцию, момент маршрута, цену,
диапазон применения и габарит одной строкой — расхождение маршрута и счёта
стало технически невозможным. Станции DRILL и CNC разводят сверловку и ЧПУ;
все станции по одной, без CNC1/2/3. Экран прайса получил диапазон применения
(`appliesBy`/`appliesFrom`/`appliesTo`) — владелец заводит работу сам, кнопка
«+ New» больше не запрещена. Полосы толщины раздвинуты до `до 7`/`8–11`/`12–19`,
фацет впервые затарифицирован своими полосами. Новая категория материала
`stock` и поле `sellsAsOwnLine` — стоковая дверь или свой рулон EVA продаются
отдельной строкой заказа (`soDraft.extraItems`), без Makeup и без геометрии.
Найдена и закрыта живая утечка русского текста на трёх экранах, построенных в
этой же сессии; полное удаление словаря `i18n.js` отложено — не видно
пользователю, риск архитектурный, не функциональный.
Проверено **502/502**, дважды — по модулям и по собранному `dist`; детали — в
шапке хендоффа v5.9.

### Предыдущее обновление · 10 сентября 2026 — прайс в справочнике и счёт по стёклам

Починен неверный счёт, который уже выставлялся: тело стекла брало одну толщину
на всю строку, и у пакета из разных стёкол отверстия, петли, нотчи и вырезы
молча оставались без ставки. Теперь считается по каждому физическому стеклу,
каждое по своей полосе. Прайс уехал из кода в справочник `DB.serviceRate` —
двадцать пять строк, правятся на вкладке Catalogues; ключи начислений при этом
не менялись, иначе отвязались бы ручные ставки в старых заказах. В Fabrication
заведены Mirror Safety Backer (по площади) и Mirror Edge Sealant (по периметру)
с меткой по центру стекла и ручным размером подписи.
Проверено **487/487**; детали и открытые ниточки — в шапке хендоффа v5.8.

### Предыдущее обновление · 10 сентября 2026 — справочники владельца

Покраска оказалась не услугой, а спандрелом: `Backpainting` и `Opaci Coat` — три
позиции справочника, а `Opaci Coat` — код производителя ICD. Цвета спандрела
перестали быть пятью словами в коде: появился справочник из шестнадцати цветов
ICD с кодами и семействами, поле в форме называется Opaci Coat. Новая вкладка
**Catalogues** даёт добавление и правку семи справочников — до неё завести
позицию было нельзя вовсе. Пересев больше не стирает работу владельца: палитра,
спандрел и фрит выведены из `REFERENCE_TABLES`, заводские строки доливаются по
id. Секция Cutout переименована в **Fabrication** по имени станции `FAB`; ключи
не тронуты. Цена фрита 3.10 → 5.00 разовой миграцией, цифровая печать выключена.
Проверено **483/483**; детали — в шапке хендоффа v5.7.

### Предыдущее обновление · 10 сентября 2026 — ставки услуг по прайсу владельца

Владелец прислал прайс «Glass Treatment Rates» и заполнил высланный ему CSV.
Одиннадцать ставок совпали с кодом точь-в-точь, шесть изменены или добавлены:
нотч ручной `10 / 15 / 20` и станочный `15 / 20 / 25` вместо прежних 15 на
любую толщину, `CNC Lami Polish` 0.28 вместо 0.35, а Patch, Cutout и митра 45°
получили ставки впервые. Ключи начислений не менялись — сохранённые заказы
читаются без миграции. Патч оказался петлёй под другим именем, ставка живёт на
виде фурнитуры; зажим и петля подтверждены как услуга, фурнитура как товар не
продаётся. Каталог целиком — `docs/SERVICE_CATALOG_2026-09-10.md`.
Проверено **481/481** по src; детали — в шапке хендоффа v5.6.

**Известный пробел, эта работа его не чинит.** Кромка и heat soak считаются по
лайтам, а тело стекла — отверстия, петли, нотчи, вырезы, пескоструй — берёт одну
толщину на всю строку. У юнита из стёкол разной толщины единой толщины нет, и
эти начисления молча остаются без ставки. Починка вынесена отдельной задачей.

### Предыдущее обновление · 10 сентября 2026 — компактная валюта и английский интерфейс

## Как правильно обновлять

> **Короткий путь: `node tools/prepush.js`.** Скрипт делает пункты 2–5, 7 и
> сам догоняет `main`, после чего пушит. Останавливается на первом же
> неуспехе и объясняет, что чинить; ничего не форсирует. Проверить без
> пуша — `node tools/prepush.js --dry`. Руками остаётся только пункт 6:
> хендофф.
>
> Зачем он появился: 11 сентября 2026 CI уронил ветку на проверке «dist не
> приходит из ветки», хотя `dist` в ветке никто не коммитил. Владелец слил
> предыдущий PR, CI пересобрал `dist` уже в `main`, и ветка осталась с
> копией «до». Это повторяется после КАЖДОГО слияния, пока работа в ветке
> продолжается.

1. **Правится модуль в `src/`, а не `dist/`.** Собранный HTML руками не
   трогают никогда — его перезаписывает сборка.
2. Новый файл модуля обязательно вносится в `build/manifest.json`, иначе он
   молча не подключится. Проверка: `node build/check-manifest.js`.
3. Проверить LF/CRLF-воспроизводимость: `node build/check-reproducible.js`.
4. Пересобрать: `npm run build:web` — в ветке обновляется только версия по
   модулям. `dist/GLASS_ERP.html` в ветку не коммитят: его пересобирает CI
   после слияния в `main`.
5. Прогнать тесты **двумя способами** — CI гоняет оба, расхождение между
   версиями больше не проскочит:
   - `node test/run.js` — по версии из модулей;
   - `TARGET=dist node test/run.js` — по собранному файлу (в ветке он не
     пересобирается, так что эта проверка честна только после `node build/build.js`).
6. Обновить `docs/GLASS_ERP_HANDOFF.md`: новый раздел сверху, версия поднята.
7. Работать в отдельной ветке и заливать через PR. `main` меняется только
   мержем; автосборка `dist` в `main` делается CI, не руками.

### `dist/GLASS_ERP.html` в ветку не коммитят — тогда конфликта нет

Робот пересобирает `dist` в `main` после каждого вливания. Если ту же сборку
переписала и ветка, при слиянии сталкиваются две разные версии полуторамега-
байтного файла, и раньше каждое слияние упиралось в ручную пересборку. Теперь
в ветке собирают без него:

```bash
npm run build:web       # только src/index.html, dist не трогается
```

CI это проверяет: если `dist/GLASS_ERP.html` пришёл из ветки, сборка падает и
подсказывает, как его убрать. Сливать нечего — конфликта не возникает.

**Автослияние для этого файла всё равно запрещено** в `.gitattributes` (`-merge`)
как последний рубеж. Без запрета git сводит две сборки текстом и молча выдаёт
файл, не соответствующий ни одной стороне: на проверке двух веток, правивших
разные css-модули, в слитом `dist` осталась одна правка из двух — а файл при
этом выглядел целым. С запретом git честно останавливается на конфликте.

Если конфликт всё же возник — например, в ветке, начатой до этого правила, —
разрешение одно: взять сборку из `main` и не пересобирать её в ветке.

```bash
git merge origin/main
git checkout origin/main -- dist/GLASS_ERP.html
git commit
```

Канонический файл всё равно соберёт CI из слитых исходников уже в `main`.
Поэтому устаревший `dist` в ветке не опасен; опасен молча склеенный.

### Чего не делать

- Не заводить вторую копию хендофа, плана или любого управляющего документа.
- При обычной правке сохранять модуль и менять его содержимое. Удаление устаревшей функции, согласованное владельцем (как отдельный Muntinbar), включает удаление её файлов, регистраций и зависимостей с проверкой оставшихся потребителей.
- Не создавать второй разбор дюймов, второй путь печати, второй переключатель
  обработки кромки. Всё это уже есть в одном экземпляре, и дубли расходятся.
