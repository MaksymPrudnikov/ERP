# Карта проекта GLASS ERP

Здесь написано **что где лежит и куда писать правки**. Сам по себе этот файл
ничего не описывает по существу — он только указывает на нужный документ.

Раньше на этом месте лежала вторая копия хендофа. Она разошлась с основной и
по номеру версии стала выглядеть свежее — из-за чего в неё писали правки,
которых потом никто не находил. Копии больше нет, вместо неё карта.

## Правило номер один: хендоф один

Управляющий документ проекта — **`docs/GLASS_ERP_HANDOFF.md`**, и он
**единственный**.

- Вторых копий не заводить. Ни в корне, ни под другим именем, ни «временно».
  Два документа с разной нумерацией уже дважды приводили к потере правок:
  сначала с планом (21 августа), потом с самим хендофом (1 сентября).
- Правка идёт **в конец шапки и новым разделом сверху**, старые разделы не
  переписываются — по ним читают историю решений.
- **Версию поднимать всегда.** Номер — единственное, по чему видно, какой
  документ свежее. Текущая версия **5.60**.

### Предыдущее обновление · 15 сентября 2026 — список Sales как в Excel

У каждой колонки списка Sales свой фильтр: галочки значений, условия как в
Looker Studio (больше, меньше, содержит, начинается с…, And / Or, Exclude) и
даты (Today … This year, свой диапазон). Активные фильтры — чипами над
таблицей, внизу итоги по отфильтрованным строкам. Колонки скрываются, добавляются
и переставляются; вид запоминается в браузере. Строки поиска нет. On Hold
ставится кнопкой слева или правой кнопкой мыши на строке, с причиной; строка
на удержании красная, Batched — серая. Проверено **608/608**, дважды; детали —
в шапке хендоффа v5.22.

### Предыдущее обновление · 15 сентября 2026 — ревизии квоты

У квоты Q-10003 появляются ревизии Q-10003-R1, Q-10003-R2: кнопка + New revision
копирует ревизию на экране. Отправленная ревизия не меняется — правка
сохраняется следующей ревизией. В Documents у квоты один бланк Quote с Valid
until (180 дней, меняется в Master Data → Company и в квоте); отмеченные
ревизии уходят одним письмом и становятся Sent. Convert to order спрашивает,
какую ревизию выбрал клиент. В списке Sales одна строка на квоту. Итогов
выигрыша на главном экране нет — это будущий отчёт. Проверено **594/594**,
дважды; детали — в шапке хендоффа v5.21.

### Предыдущее обновление · 15 сентября 2026 — статусы заказа и квоты

У заказа статусы New → Verified → Batched 🔒 → Ready → Picked up / Delivered →
Closed и Cancelled, у каждого шага дата; следующий шаг — одна кнопка в шапке.
Батч закрывает строки: размер, Makeup, фигуру и кромку не поменять, изменение —
новая строка «added after batch» или новый заказ. Перед верификацией и батчем —
окно, если cash-клиент не внёс депозит или кредит сверх лимита; при выдаче — если
есть долг; Take payment открывает оплату на заказ. В списке Sales галочки Show
Orders / Quotes и чипы статусов; квота Q-… превращается в заказ кнопкой Convert
to order и остаётся Won. Проверено **584/584**, дважды; детали — в шапке
хендоффа v5.20.

### Предыдущее обновление · 14 сентября 2026 — оплаты клиентов

### Предыдущее обновление · 14 сентября 2026 — бланки заказа

Кнопка Documents в шапке заказа открывает Work order, Proforma invoice и Order
confirmation. Под каждой строкой — её стекло, камера и сервисы с базой и

## Как правильно обновлять

> **Короткий путь: `node tools/prepush.js`.** Скрипт делает пункты 2–5, 7 и
> сам догоняет `main`, после чего пушит. Останавливается на первом же
> неуспехе и объясняет, что чинить; ничего не форсирует. Проверить без
> пуша — `node tools/prepush.js --dry`. Руками остаётся только пункт 6:
> хендофф.
>
> Зачем он появился: 11 сентября 2026 CI уронил ветку на проверке «dist не
> приходит из ветки», хотя `dist` в ветке никто не коммитил. Владелец слил
> предыдущий PR, CI пересобрал `dist` уже в `main`, и ветка осталась с
> копией «до». Это повторяется после КАЖДОГО слияния, пока работа в ветке
> продолжается.

1. **Правится модуль в `src/`, а не `dist/`.** Собранный HTML руками не
   трогают никогда — его перезаписывает сборка.
2. Новый файл модуля обязательно вносится в `build/manifest.json`, иначе он
   молча не подключится. Проверка: `node build/check-manifest.js`.
3. Проверить LF/CRLF-воспроизводимость: `node build/check-reproducible.js`.
4. Пересобрать: `npm run build:web` — в ветке обновляется только версия по
   модулям. `dist/GLASS_ERP.html` в ветку не коммитят: его пересобирает CI
   после слияния в `main`.
5. Прогнать тесты **двумя способами** — CI гоняет оба, расхождение между
   версиями больше не проскочит:
   - `node test/run.js` — по версии из модулей;
   - `TARGET=dist node test/run.js` — по собранному файлу (в ветке он не
     пересобирается, так что эта проверка честна только после `node build/build.js`).
6. Обновить `docs/GLASS_ERP_HANDOFF.md`: новый раздел сверху, версия поднята.
7. Работать в отдельной ветке и заливать через PR. `main` меняется только
   мержем; автосборка `dist` в `main` делается CI, не руками.

### `dist/GLASS_ERP.html` в ветку не коммитят — тогда конфликта нет

Робот пересобирает `dist` в `main` после каждого вливания. Если ту же сборку
переписала и ветка, при слиянии сталкиваются две разные версии полуторамега-
байтного файла, и раньше каждое слияние упиралось в ручную пересборку. Теперь
в ветке собирают без него:

```bash
npm run build:web       # только src/index.html, dist не трогается
```

CI это проверяет: если `dist/GLASS_ERP.html` пришёл из ветки, сборка падает и
подсказывает, как его убрать. Сливать нечего — конфликта не возникает.

**Автослияние для этого файла всё равно запрещено** в `.gitattributes` (`-merge`)
как последний рубеж. Без запрета git сводит две сборки текстом и молча выдаёт
файл, не соответствующий ни одной стороне: на проверке двух веток, правивших
разные css-модули, в слитом `dist` осталась одна правка из двух — а файл при
этом выглядел целым. С запретом git честно останавливается на конфликте.

Если конфликт всё же возник — например, в ветке, начатой до этого правила, —
разрешение одно: взять сборку из `main` и не пересобирать её в ветке.

```bash
git merge origin/main
git checkout origin/main -- dist/GLASS_ERP.html
git commit
```

### Чего не делать

- Не заводить вторую копию хендофа, плана или любого управляющего документа.
- При обычной правке сохранять модуль и менять его содержимое. Удаление устаревшей функции, согласованное владельцем (как отдельный Muntinbar), включает удаление её файлов, регистраций и зависимостей с проверкой оставшихся потребителей.
- Не создавать второй разбор дюймов, второй путь печати, второй переключатель
  обработки кромки. Всё это уже есть в одном экземпляре, и дубли расходятся.
